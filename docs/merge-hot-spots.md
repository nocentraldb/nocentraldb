# Merge hot spots

Two pull requests that each add their own entry should not conflict (NOC-512). Git conflicts when two branches change the same lines, or insert at the same place. A file that every feature appends to at the same place is a hot spot.

This list comes from the last 50 pull requests merged into `main` before NOC-512, #422 to #488. It counts how many of them changed each file that already existed; a new file conflicts with nothing. It names every file that four or more of them changed, and says for each whether the hot spot is gone or why it stays.

## Removed

| File | PRs | What they changed | Now |
| ---- | --: | ----------------- | --- |
| `texts/texts.json` | 8 | A new text, in id order, next to the other new texts of the same feature | One file per text, `texts/<kind>/<name>.json` ([texts/README.md](../texts/README.md)) |
| `crates/nocentraldb/src/texts/error.rs`, `bridge.rs` and the other generated text modules | 4 and 3 | The new text's constant, in id order, so beside the feature's other new texts | The modules list their texts by a hash of their ids, so two new texts land side by side only by chance, about once in as many texts as the module holds. When they do, take either side of the generated file and run `node scripts/texts.mjs --write` |

Change fragments were no hot spot: each pull request adds its own file under `changes/`.

## Waiting for the owner

| File | PRs | What they changed |
| ---- | --: | ----------------- |
| `docs/rfc/0009-sdk-api.md` | 11 | Mostly a line at the end of "Decisions" and of "History", besides the section the feature changes |

How an RFC's History line is written without two pull requests conflicting is the owner's choice, NOC-517. Until it is decided these lists stay as they are.

## Staying

| File | PRs | What they changed | Why it stays |
| ---- | --: | ----------------- | ------------ |
| The rest of each RFC | | The section the feature specifies | An RFC states the current design as one complete text, so a feature changes it where it applies. Two pull requests conflict there only when they change the same passage, and then they need a person to reconcile the design |
| `crates/nocentraldb/src/lib.rs` | 6 | A `mod` line, often with a `#[cfg(test)] mod <name>_tests;`, and a `pub use` line | Rust declares each module in its parent. rustfmt keeps the declarations sorted, so two new modules conflict only when their names are neighbours. The `pub use` lines are the SDK's public names, which belong in one place |
| `crates/nocentraldb/src/sync/tests/mod.rs` | 5 | A `mod` line for a new test file | As for `lib.rs`: Rust needs the declaration, and the sorted list conflicts only between neighbours |
| `crates/ncdb-core/src/view/mod.rs`, `crates/nocentraldb/src/bridge/mod.rs`, `crates/ncdb-relay/src/sqlite.rs` | 6, 4, 4 | Code: the view's fold, the bridge's dispatch of requests, the relay's SQLite store, and their `mod` lines | Feature code in the place it belongs. Pull requests change different functions, so they rarely meet |
| `packages/sdk/etc/api-report.d.ts` | 6 | The TypeScript SDK's public declarations, generated by `tsc` | The gate `repo:api-report` holds the public surface in one reviewed file. It follows the declarations' order in the source, so two additions meet only where they touch the same interface. On a conflict, take either side and run `node scripts/release/api-report.mjs --write` |
| `packages/sdk/src/db.ts` | 5 | The types of the TypeScript SDK's public API | Feature code: each feature changes its own interface |
| `docs/rfc/README.md`, `site/src/content/docs/docs/rfcs.md` | 5, 4 | A row for a new RFC, at the end | The RFCs are listed by number. A new RFC comes about once a week, and two at once conflict on the last row only |
| `docs/repository.md` | 6 | The layout, and the gate table's rows, each one long line | One line per project in the gate table, so two changes to the same project's gates conflict. The table is the one place that lists every gate, and `scripts/contributor-kit.test.mjs` holds it to the gates that run |
| `docs/bulk-import.md`, `docs/release-management.md`, `docs/relay-deploy.md`, `docs/getting-started-browser.md` | 5, 4, 4, 4 | The guide's text for a feature | Prose a feature changes where it applies, as for an RFC |
