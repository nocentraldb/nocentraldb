# 2026-11-12 · NOC-266 · The view holds the shipped account model's collections as `$members`, `$memberships`, `$links`, `$statements` and `$wrappedKeys`, and folds each space by the one model its genesis names

- Decided by: coding agent (NOC-266), following RFC 0010's decided text ("The account space"; Carsten, 2026-11-12, NOC-273), which puts the account space's tables beside the app's under names that start with `$`, reserved for the core by RFC 0005 ("Names")
- Why: the names are the model's own collection names with `$` in front, so no app collection can take one. They are view-internal: changes of the account space name the collections without the `$`, and the core adds it only where a space's genesis names the shipped model's id. A space of the app's model never reaches a `$` table, and a space of the shipped model never reaches the app's. The shipped model comes to the view with the registry (`Registry::with_reserved_model`), as plugin code does. Its collections sit in the view's one model, so the model hash, migrations, refolds and rebuilds cover them without a second path. A model without a shipped one hashes as before, so existing views stay current. Adding a shipped model folds the view again, so that changes parked as "another model" fold.
- Instead of: a second view model with tables of its own and a fold that switches models per space, which would need every refold, migration and rebuild path twice; or a prefix such as `account_` that an app could also declare.
