# 2026-11-16 · NOC-347 · A browser window without OPFS refuses to open the database instead of keeping a temporary copy in memory

- Decided by: owner (Carsten, 2026-11-16, in chat with pm), reversing RFC 0006 decision 12 (decided A on NOC-34, confirmed by NOC-58)
- Why: in a private window of Safari or Firefox there is no OPFS, so the copy lived only in the memory of the tab that owned the database. When that tab closed, or was hidden and another tab took over (NOC-332), the next owner opened an empty copy, and the changes the relay had not confirmed were lost without a word: `unconfirmed` read 0 afterwards (measured in WebKit and Firefox, NOC-347). In the owner's words: "The point of a private window is to store nothing. The point of a local-first app is to store." So `nc.open` fails with `storageUnavailable` where OPFS is missing, and the app explains it to the user. Chromium's private window is not refused: it has OPFS, the SDK cannot tell it from a normal window, and its copy outlives the owning tab.
- Instead of: keeping the database with a hidden owner while the copy is in memory, which saves the copy only across tab switches (option A); a durability field that reports the loss after a handover, which reports the loss but does not prevent it (option B); both together (option C); the in-memory copy with `storage: "temporary"` as before.
