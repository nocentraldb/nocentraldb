# 2026-11-10 · NOC-200 · A grant is lost only when an entry concurrent with it capped it, an add's cap included

- Decided by: coding agent (NOC-200), with pm, following RFC 0008's text
- Why: RFC 0008 calls a grant lost when "a revocation it did not see capped" it ("Concurrent add and remove of one member"; "The function"), and Bob "can repeat the grant once he has seen the removal". `resolve` marked every grant whose effective role ended below its role, which took in a grant that a later removal or demotion saw and revoked on purpose, such as the add of every member ever removed. `Verdict::Lost` now marks a grant only when an accepted entry about the same member caps it below its role and the two are concurrent: neither is in the other's causal past. This is NOC-190's rule (`2026-11-10-NOC-190-a-lost-grant-is-one-a-concurrent-revocation-capped.md`), with one difference: the capping entry may also be an add, because RFC 0008 ("Roles") says every membership entry caps the grants that did not see it and "every cap is a revocation", so of two concurrent adds of one member the higher one stays lost, as `two_concurrent_adds_of_one_member_leave_the_lower_role` already asserted. The role computation is unchanged; only the verdict is.
- Instead of: counting only removes and set roles as caps, which would turn the higher of two concurrent adds from lost into accepted although it has no effect; keeping the old verdict and filtering it in each SDK.
- Topics: membership, rfc-0008
