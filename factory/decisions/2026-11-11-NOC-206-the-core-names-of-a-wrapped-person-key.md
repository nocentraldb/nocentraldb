# 2026-11-11 · NOC-206 · The core wraps a person key with `wrap_person_key` and `unwrap_person_key`, and holds it as `keys::PersonKey`

- Decided by: coding agent (NOC-206); the bytes are the owner's (Carsten, 2026-11-11, NOC-209 A)
- Why: the core's names follow the key chain's, which seals a key under a subkey the same way: `membership::wrap_person_key(space_key, space, generation, person_key_id, &key) -> [u8; WRAPPED_PERSON_KEY_LEN]` with a random nonce, `wrap_person_key_with_nonce` for test vectors, and `unwrap_person_key(...) -> Option<PersonKey>`, which is `None` for anything that is not 72 bytes or does not open under that key, space, generation and person-key id. The person key is a secret type of its own in `keys`, `PersonKey`, like `SpaceKey`: wiped on drop, its `Debug` hidden, its bytes visible only inside the crate, with `PersonKey::commitment` for the commitment a member checks after unwrapping. `membership::PersonKey`, the folded state of a person key's entries, keeps its name; the two live in different modules.
- Instead of: raw `[u8; 32]` person keys, which could be printed or logged; a second name such as `PersonKeySecret` for the secret, which would read unlike `SpaceKey` and `MemberKey`; checking the commitment inside `unwrap_person_key`, which needs the log's commitment and belongs to the member that reads the record.
