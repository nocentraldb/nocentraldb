# 2026-11-09 · NOC-67 · How the core reads a control body where RFC 0008 leaves a detail open

- Decided by: coding agent (NOC-67)
- Why: RFC 0008 draws the control body but leaves some reading rules open, and each has to be one rule on every member and the relay. Key 3 is required in every body, `[]` in a genesis, as payload key 3 is required in RFC 0002; a genesis with dependencies, or another entry without any, is malformed ("a control change without control dependencies that is not a genesis is malformed"). Keys 0, 2 and 4 to 7, and a key from 8 to 63 the entry type does not define, make the body not understood, so the change is parked as RFC 0002 parks what it does not understand, and a newer client can still define them. A key the action does not use (a role on a remove, a from generation on a reader's set role, a cutoff on an add) or a missing one is malformed, so each entry has one encoding; a set role carries key 14 exactly when its role writes. An add whose keys 11 and 12 do not hash to its subject, and a certificate with a key RFC 0003 does not list, are malformed. Entry types 2 to 6 are kept with their fields as they are, for the tickets that read them; entry types from 7 up are parked.
- Instead of: accepting a missing key 3 as no dependencies, or an unused key as ignorable, which would give one entry two encodings and two change ids.
- Topics: membership, rfc-0008, encoding, parking
