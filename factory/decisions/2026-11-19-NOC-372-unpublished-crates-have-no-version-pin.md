# 2026-11-19 · NOC-372 · A crate with publish = false is declared in [workspace.dependencies] with its path and no version

- Decided by: pm, NOC-372, on the coding agent's proposal
- Why: cargo keeps a dev-dependency that carries a version in the packaged manifest, and crates.io must resolve it. So `cargo package -p ncdb-core` failed on `ncdb-harness = "=0.1.0"`, a crate that is not published. Cargo drops a dev-dependency without a version when it packages a crate. So only a published crate is pinned to `=<version>`; an unpublished one keeps `path` alone. check-version rule 4 reads the publish flag at the entry's path and checks both cases, and set-version pins only published crates. A new rule 8 makes the gate fail when a published crate uses an unpublished one in `[dependencies]` or `[build-dependencies]`, which cargo would otherwise only refuse in the publish job. This amends NOC-18's rule that every path entry in `[workspace.dependencies]` is pinned (docs/release-management.md, "Versioning"). Its reason, that a prerelease of a sibling crate must resolve, matters only between published crates; crates.io must resolve every versioned dependency, dev-dependencies included.
- Instead of: publishing `ncdb-harness` and `ncdb-test-counter` only so that `ncdb-core`'s and `nocentraldb`'s tests resolve, which puts test crates on crates.io for good; or moving the tests that use them into an unpublished crate, which splits the core's tests from its code.
- Topics: release, cargo, crates-io, gates, dependencies
