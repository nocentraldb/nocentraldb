# 2026-11-12 · NOC-175 · Syncing gets a transport seam and a clock of its own, with no change natively

- Decided by: coding agent (NOC-175, sync slice, step 1), as pm scoped it
- Why: the Rust SDK's session and run loop talk to the relay through tokio-tungstenite and wait with tokio's timers and `std::time::Instant`, none of which exist on wasm32-unknown-unknown (`Instant::now` panics there). Before the browser's WebSocket can carry a session, the session must not name them. `sync::time` gives `Instant`, `sleep`, `sleep_until` and `timeout`: natively they are tokio's and std's, so nothing changes; on wasm32 they are the global's `setTimeout` and `performance.now()` through `js_sys`, which the crate already depends on, so no dependency or feature is added. `sync::transport::Transport` carries binary messages each way (`send`, `recv`), and the native tokio-tungstenite WebSocket moves behind it unchanged: RFC 0007's largest message as the limit, rustls with the platform's roots, control frames skipped. `Session` is generic over it.
- Instead of: a trait object (`Box<dyn Transport>`), which async methods in a trait do not allow without boxing every future; `web-time` for the clock, a new crate NOC-210 Q2 B did not take; keeping `tokio::select!` out of the session now, which the browser step needs anyway (tokio's "macros" on wasm32, for the owner's tick there).
- What this does not do: the browser's WebSocket, the run loop on wasm32, the `fetch()` client for large changes, and lifting `Db::open`'s refusal of a relay on wasm32, which follow in their own PR with the owner's NOC-245 answers.
- Topics: sdk-rust, sync, wasm, browser
