# 2026-11-23 · NOC-445 · A browser database whose files were dropped is refused with `storageLost` until the app opens it with `ifStorageLost: "open-empty"`

- Decided by: pm (2026-11-23, NOC-445: option B with A, which the owner agreed to on the ticket); the refusal over a flag and the names `storageLost` and `ifStorageLost` are the coding agent's proposal, for the owner's review in the PR
- Why: in a Chromium private window, OPFS goes after about ten minutes with no database open, while IndexedDB, with the member key, stays (measured in Chromium 157: OPFS kept after 450 s, gone after 600 s; IndexedDB, sessionStorage and localStorage kept after 660 s). The next `nc.open` started an empty copy under the same key, and without a relay all data was lost without a word, against "Nothing is lost silently". So the SDK records each database it opened in IndexedDB (`nocentraldb-opened`, store `names`) and as an empty twin file on OPFS (`.nocentraldb-opened/<name>`), in every browser, since it cannot tell a private window from a normal one; an open that finds the record without its twin fails with `storageLost` before the worker starts, and keeps failing until the app opens with `ifStorageLost: "open-empty"`. IndexedDB over sessionStorage: a worker reaches it, it is shared by every tab of the window, and the member key lives there, so the record goes exactly when the key goes.
- Instead of: documenting the drop only (option A alone), which leaves the loss silent for the app; opening empty with a flag on `db.durability`, which an app that never reads it misses; keeping OPFS alive after `close()` (option C), a timer that outlives the database and still loses everything when the tab closes; a marker in sessionStorage, which a new tab of the same window does not share.
