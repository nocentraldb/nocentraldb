# 2026-11-10 · NOC-103 · The relay server bounds each connection's outgoing queue and closes a member that takes nothing for 60 seconds

- Decided by: coding agent (NOC-103), within RFC 0007's "Subscribe" and "Liveness"
- Why: each connection holds at most 32 outgoing messages (at most 4 MiB, since a message is at most 128 KiB). Whoever produces a message, the request loop or a subscription, waits for room in the queue instead of dropping it. A subscription therefore reads the log only as fast as its member takes the entries, and a slow reader gets every entry, in order, without the server buffering the space for it; while the queue is full the connection reads no further requests either. A member whose connection takes no message for 60 seconds is closed: "Liveness" lets a relay close any connection at any time, and the member reconnects and resubscribes from its cursor, so it misses nothing. The close drops the TCP connection without a close frame, since a socket that takes nothing would not take one either; RFC 0007 defines no close code, and a member resumes from its cursor whatever ends the connection.
- Instead of: dropping live entries for a slow member, as AWS's best-effort delivery does, which leaves a gap the member sees only at the next entry; closing a connection as soon as its queue is full, which would also close a member that catches up a long log through `subscribe`; or an unbounded queue, which lets one member that stops reading hold a copy of every entry appended after it stopped.
- What this does not do: the opening handshake (WebSocket upgrade, `hello`, `auth`) has no timeout yet, so a connection that never completes it holds one task until the peer goes away.
- Topics: relay, rfc-0007, liveness
