# 2026-11-22 · NOC-422 · A change is held in memory as its bytes, and never as one tree of values

- Decided by: coding agent (NOC-422)
- Why: a `cbor::Value` tree takes many times the bytes of its encoding (a map of two entries allocates a B-tree node of eleven slots, about 720 bytes), so a change of 15.5 MB peaked at 1.1 GB on the writer and 610 MB on a receiving device. The core now encodes and decodes the payload one operation at a time, the header and the frame straight from and into their buffers, and keeps each operation's value (key 5) as the canonical bytes the change carries, which `Operation::value` decodes on read. A `Change` keeps the frame's bytes once, the header bytes and the signature as ranges of them, plus the header's payload. The log keeps the `Change` it is handed, never a copy, and a write hands its change to the log. Bytes a streaming read does not take are decoded as one tree, as before, so every error stays what it was. Code that reads or writes a change, a payload or an operation follows the same rule; `tests/memory_seal.rs` of ncdb-core, and `memory_write.rs` of nocentraldb and `memory_bridge.rs` of nocentraldb-wasm, hold the peaks to it.
- Instead of: a `cbor::Value::Map` backed by a sorted vector, which would shrink every tree but changes the plugin API of the published crate `ncdb-plugin`, the owner's; or folding the operations straight from the decrypted bytes, which would change the `Checks` trait and every caller of `open`, for little more.
- What this does not do: a decoded operation still takes about three times its bytes, and a write about eight times its change's bytes at its peak; the log in memory still keeps every change of every space (frame and payload, twice its ciphertext), which grows with the log, not with a change.
