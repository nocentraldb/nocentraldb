# 2026-11-10 · NOC-192 · The relay server logs a failed accept and tries again after a pause; only a listener that is gone ends it

- Decided by: coding agent (NOC-192)
- Why: `Server::run` returned on any error from `accept`, so running out of file descriptors (EMFILE, ENFILE), which lasts only until connections close, stopped the whole server and dropped every member. Now an error ends `run` only when it means the listener itself is gone, as `accept(2)` names it: EBADF, EINVAL, ENOTSOCK or EOPNOTSUPP (on other platforms, `InvalidInput`). Any other error is written to stderr as one line that holds only the operating system's message, and `accept` is tried again after a pause of 10 ms that doubles while the error lasts, up to 1 s, and starts over after the next accepted connection. The pause matters: a connection the server cannot accept stays in the kernel's queue, so retrying at once would spin at full CPU while the descriptors stay taken. `libc` becomes a direct dependency on Unix to name these errno values; it was already in the tree through tokio, at the same pinned version.
- Instead of: treating every error as transient, which would keep a server with a dead listener running and logging forever; returning on any error, the old behaviour; telling errors apart by `io::ErrorKind`, which maps EBADF, ENOTSOCK and EOPNOTSUPP to no kind of their own; or a logging library, which the crate does not have yet, for one line on stderr.
- What this does not do: it does not free descriptors. While they are taken, new connections wait in the kernel's queue or time out at the member, which reconnects with back-off. A lasting error writes one line a second to stderr.
- Topics: relay, liveness
