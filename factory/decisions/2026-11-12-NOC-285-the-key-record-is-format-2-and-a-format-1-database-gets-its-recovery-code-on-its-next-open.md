# 2026-11-12 · NOC-285 · The key record is format 2, and a format 1 database gets its recovery code and statement number 1 on its next ordinary open

- Decided by: Carsten (2026-11-12, on NOC-285, points 3 and 4, as recommended)
- Why: RFC 0003 fixed the key record at format 1, 113 bytes, and GENESIS reserves key formats for the owner; a device must also keep its account key statement, the recovery code until `confirm()` (NOC-273), and which of three states the database is in. Format 2 is the magic string, the byte `2`, the member signing and agreement secrets, then an account byte: `0` no account yet (waiting to be paired); `1` a device, followed by the account secret (32), the recovery key (32), the number (8, big-endian) and the statement signature (64); `2` an agent, followed by the account key (32), the certificate signature (64), the recovery key, the number and the statement signature. Then a code byte: `0`, or `1` and the code's 16 bytes. Sizes: 83 bytes waiting to be paired, 219 for a device (235 while it holds the code), 283 for an agent. The SDK still reads format 1 and writes format 2 on the next open; in the browser the sealed record keeps its IV and tag. A database with key record format 1 has an account key but no recovery key: its next ordinary open creates the recovery code and statement number 1 for that account key and hands the code to the app as on a new account; entries already written stay as written. No app has shipped on these databases yet, so this mainly covers test and demo data.
- Instead of: no alternative was offered on the ticket for points 3 and 4; the decision took the recommendation.
