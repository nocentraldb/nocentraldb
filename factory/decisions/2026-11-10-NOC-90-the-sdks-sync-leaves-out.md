# 2026-11-10 · NOC-90 · What the Rust SDK's sync leaves out, and the Rust names it uses until the owner confirms them

- Decided by: coding agent (NOC-90), as a safe subset; pm told on 2026-11-10
- Why: the ticket asks for push, pull, subscribe, reconnect, the epoch and the counts of the sync status. Built: `OpenOptions::relay(url)`, `Db::sync()` returning `SyncReport`, whose `current()` returns `SyncStatus { connection, unconfirmed, refused, epoch_changed, error }` with `Connection::{Connected, Connecting, Offline, Paused, None}`, RFC 0009's table in Rust case. RFC 0009 names `db.sync.current` but no Rust type, and `Sync` would shadow std's marker trait, so these three names are provisional until the owner answers NOC-116. Left out, each with its follow-up ticket: a handle to write into a space the member was added to, whose changes are pulled and folded, with `spaces().get` and `spaces().list` (NOC-119, which NOC-91 needs); `db.sync().subscribe()`, `pause()`, `resume()`, `is_confirmed()`, `confirmed()`, the per-space `status`, and pushing a refused change again (RFC 0008, M19) (NOC-120); TLS, so `Db::open` refuses a relay URL that is not `ws://` with `InvalidValue` rather than retrying a connection that can never open, and a large change's download link (NOC-121); the epoch and the cursors on disk (NOC-108). A pulled change wakes every subscription of its space, since the SDK does not decrypt to learn its collections.
- Instead of: guessing more public names the owner has not seen, or retrying a `wss://` relay forever as `offline`.
