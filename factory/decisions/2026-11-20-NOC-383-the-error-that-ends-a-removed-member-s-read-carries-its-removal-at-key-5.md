# 2026-11-20 · NOC-383 · The error that ends a removed member's read carries its removal at key 5, an entry with its frame inline

- Decided by: coding agent, NOC-383, for the owner's review in the PR (the wire format is the owner's)
- Why: the removal must reach the member in the message that ends its sync, so that it cannot get lost between a page and the error. `error` gains key 5, `removal`, a log entry as `entries` carries one (`{1: position, 2: accepted at, 3: frame}`), on `not_member` and `removed_member` answers to a pull or a subscription of a member whose latest accepted revocation removed it; the relay finds it by `resolve` of the space's control changes. The SDK folds it, records its position and leaves its cursor where it was, so it never treats the removal as a page with a gap. An SDK that does not know key 5 ignores it, as it ignores any key it does not read. The frame always travels inline: a removal is a small control change; should one ever not fit, the error comes without it. A stranger, a push, and every other code get no removal.
- Instead of: an `entries` page holding only the removal before the error, which breaks the rule that a page's positions are dense and would make the member pull the gap again; a message type of its own, which adds a type for what is part of the error; serving the removal only when the subscription ends live, which misses a member that was removed while offline and asks again on reconnect, the case RFC 0008 describes.
- Topics: relay, wire-format, rfc-0007
