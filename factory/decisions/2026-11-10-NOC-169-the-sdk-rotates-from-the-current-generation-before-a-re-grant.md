# 2026-11-10 · NOC-169 · The SDK rotates from the current generation before a re-grant, and refuses a space with a person key

- Decided by: coding agent (NOC-169), inside the owner's NOC-154 point 2 (Carsten, 2026-11-10: re-adding a former member rotates first)
- Why: RFC 0008 ("Membership entry", "A member demoted and raised again") has a re-grant name a fresh generation whose key chain entry its author wrote, and has an admin rotate first. It leaves open which previous generations the rotation lists and which revocations it answers. The SDK's rotation (`members/rotate.rs`) lists the current generation only, the one its author writes with, so it needs only that key; it answers no revocation, since a re-grant answers none; and it writes, in this order, the key chain entry, one envelope of the new key per member of the space, the author included, in member-id order, then the add from the new generation and the new member's envelope, all under the author's next sequences. The control changes before the add carry the old generation in their header, the add and its envelope the new one, which is current once the author's own envelope is folded. A space that holds a person key is refused with `InvalidValue` before anything is written: a rotation must re-wrap its person-key records (RFC 0003, step 3), and the SDK holds none of those records, which live in the relay's person-key store. `members().remove` and `set_role` will use the same rotation once NOC-203 names how they take a member.
- Instead of: listing every head, as a merge rotation does, which needs the key of every head and is RFC 0008 step 5's own case; writing the rotation without its person-key records, which would leave the person's fields unreadable under the new generation for members added later; answering the former member's removal, which an earlier rotation may have answered already.
- What this does not do: it does not merge concurrent generations, and it does not re-wrap person-key records. Each change is folded in its own transaction. A crash between them leaves a rotation without every envelope, or without the add; a crash before the author's own envelope leaves the author without the key of the generation that is now current, so it cannot write into the space until another admin sends it an envelope or rotates again. Writing the whole rotation in one transaction needs a core change and is a follow-up.
