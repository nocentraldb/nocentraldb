# 2026-11-10 · NOC-86 · An encrypted previous key is 72 bytes, and a merge rotation seals each head's key

- Decided by: Carsten, 2026-11-10 (NOC-97, option A), for the layout; coding agent (NOC-86) for how the core builds it
- Why: RFC 0003 ("Key-chain subkey") fixes the subkey, the cipher and the associated data, but not the byte layout of an encrypted previous key, a wire format. The owner chose NOC-97 A: nonce (24) ‖ ciphertext (32) ‖ tag (16), 72 bytes, XChaCha20-Poly1305 with a random nonce, the layout of a sealed payload and of the genesis's model id. The core builds it in `membership::seal_previous_key`, and opens it in `open_previous_key`, a local check the fold never calls. The associated data is the space id (16 bytes), the new generation id and the previous generation id (8 bytes each, big-endian), with no label: RFC 0003 lists exactly those three, and the subkey's info already carries the label; the 8-byte big-endian ids follow the subkey's info. A key chain entry whose encrypted key is not 72 bytes is malformed, so each entry has one encoding. `Resolved::merge_rotation(admin)` gives the merge rotation (the derived generation id, every head as previous, the current members as recipients), and `MergeRotation::entry` seals each head's key under the new generation's key; without the key of a head there is no entry, since an admin cannot merge a generation it does not hold. A merge rotation answers no revocation, so its key 10 is empty. When to write it, after a random delay (M15), is the SDK's. tests/vectors/membership/generate.py writes the vector with cryptography and PyNaCl. NOC-106 writes the layout into RFC 0003.
- Instead of: a CBOR map of nonce and ciphertext (NOC-97 B), or a deterministic nonce (NOC-97 C), which the owner did not choose; or a label in the associated data, which RFC 0003 does not list.
- Topics: rfc-0003, rfc-0008, keys, encoding, membership
