# 2026-11-12 · NOC-276 · A push is idempotent for a change's own author, even after the change ended its membership

- Decided by: coding agent (NOC-276), following RFC 0007, "Push" ("A push is idempotent: if the connection drops before `pushed` arrives, the member pushes the same frames again and gets `duplicate` for the ones that made it")
- Why: a member's leave can be appended while its answer is lost. The member then got `not_member` for the space and kept the leave unconfirmed forever, which is the timeout NOC-276 tracked in the merge test. So the relay core answers `duplicate` for a change it holds whose author is the uploader, before the uploader check. The author already holds the change, so it learns only the position its first push would have told it. Anyone else still has to be a current member first. And the SDK pushes a space's unconfirmed changes once more when the relay first stops the space: the relay confirms the ones it holds as duplicates and refuses the rest with `not_member`, so `unconfirmed` reaches 0 and `refused` counts what the relay never got. The push is marked when the space is stopped, not on every `not_member`, so the push's own `not_member` cannot start a loop; a push that a lost connection interrupts runs again on the next connection.
- Instead of: answering `duplicate` to any former member, which would tell it the positions of other members' changes; counting a stopped space's unconfirmed changes as refused without asking the relay, which would call a leave the relay holds refused; or leaving it unconfirmed, which `unconfirmed` and durability report as at risk forever.
- Topics: relay, sync, push, membership
