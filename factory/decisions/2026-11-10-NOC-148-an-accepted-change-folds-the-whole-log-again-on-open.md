# 2026-11-10 · NOC-148 · An accepted change of the view's model folds the whole log again, before open returns

- Decided by: coding agent (NOC-148), the safe subset
- Why: RFC 0006 ("Rebuilding the view") adds a column or table for an additive change and folds only the parked operations, and RFC 0009 ("What `nc.open` does", step 4) lets `nc.open` resolve while a full rebuild runs, with `db.view` reporting its progress, a public name the Rust SDK does not have yet. Folding every change of the log again into new tables, in the transaction that opens the view, gives the same view, since each field's state is a function of its set of operations (RFC 0004), covers every accepted change (a new field, collection, option, target or index, a rolled-back lock) with one path, and leaves the database as it was if anything fails. `View::open_with` takes the member's checks for it; `View::open`, which has none, refuses such a change with `Error::Model`.
- Instead of: the incremental path of RFC 0006 for each kind of accepted change, each a path of its own to prove equal to a rebuild; or a rebuild in the background, which needs `db.view` in the Rust SDK.
- What this does not do: opening after a change of the model costs time in proportion to the log, and the app waits for it; the incremental path and the progress report are follow-up NOC-156.
