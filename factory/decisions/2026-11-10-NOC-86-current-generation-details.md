# 2026-11-10 · NOC-86 · The current generation where RFC 0008 leaves a detail open

- Decided by: coding agent (NOC-86)
- Why: RFC 0008 ("Two removals that rotate the key at once", step 3) makes the current generation a head of the generation graph, a generation that no accepted key chain entry lists as previous, with the highest ordinal, then the one whose key chain entry comes first in the order; it leaves open what happens with a generation that two key chain entries name (M23), and with a rotation that is rejected. (1) A generation named by more than one key chain entry is never a head: it may stand for two keys under one id, which RFC 0008 builds generation ids to prevent. An accepted entry for such a generation lists nothing, so the generations before it stay heads, and the first generation, which no entry can name, keeps at least one head in every graph. (2) A generation whose only key chain entry was valid when written but is rejected in the end (M17) is a head and can be current; its entry lists nothing. M17's reason says the exposure rule makes the next admin rotate away from it, which needs it to be current. (3) Among heads of equal ordinal, the entry's place in the order of step 4 decides. Only the first generation has ordinal 1, so it never ties. (4) `Resolved::encode` carries the current generation, so the convergence harness compares it.
- Instead of: letting an ambiguous generation be current, so that members seal under an id that may name two keys; or leaving rejected rotations out of the heads, so that a generation a removed admin holds is never rotated away from.
- Topics: rfc-0008, keys, convergence, membership
