# 2026-11-20 · NOC-389 · A member tries every key the envelopes of a generation unwrap to

- Decided by: Carsten, 2026-11-20 (option A on NOC-389)
- Why: a member kept one key per generation, the last envelope's, so a wrong-key envelope that arrived last made it reject sealed changes it could read: its own verdict depended on arrival order (principle 2), and a member who can write an envelope could blind another member to a generation. The core now keeps every key the envelopes to it unwrap to, by envelope change id, and tries each when it opens a sealed change, a key chain entry or the genesis's sealed `model.id`. Whether an envelope holds the right key stays a local check (RFC 0008, "What the fold may read"): nothing on the wire or on disk changes. Three choices sit below that decision, for the owner's review in the PR. First, a ciphertext counts only when exactly one held key opens it, since XChaCha20-Poly1305 does not commit to its key (RFC 0003, "Primitives"). Second, the key a member writes under is the one the generation's own control change opens under: the genesis for the first generation, the key chain entry for a later one. With several keys and no such change, the member has no key to write under yet. Third, `SealChecks::wrong_envelopes` lists each envelope that change does not open under, with its author; the SDK does not show it yet.
- Instead of: keeping only the first envelope per generation in change id order (option B), which is order-independent too, but a wrong envelope with a lower id would still blind the member; folding a change that any held key opens, which would let an author who knows a wrong key show one member a plaintext the others do not read.
- Topics: crypto, keys, membership, convergence
