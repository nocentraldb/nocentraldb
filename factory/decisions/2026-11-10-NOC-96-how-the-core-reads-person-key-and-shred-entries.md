# 2026-11-10 · NOC-96 · How the core reads person-key and shred entries where RFC 0003, RFC 0007 and RFC 0008 leave a detail open

- Decided by: coding agent (NOC-96); the bytes a record's writer signs by the owner (Carsten, 2026-11-10, NOC-117 A, as built)
- Why: the bodies follow RFC 0008 key by key; a sign-off map with any key besides 1 and 2, or of the wrong length, makes the shred malformed, since RFC 0003 defines no extension for it. The record hash a person-key entry announces is the SHA-256 of the record's wrapped bytes, as RFC 0008 says ("SHA-256 of the wrapped record bytes"). A record's writer signs `H("nocentraldb/person-key-record" || space id || person-key id || generation (8 bytes, big-endian) || writer member id || wrapped bytes)`, following RFC 0003's rule that every hash input starts with its context and has fixed-length fields before the one of variable length; the space id keeps a record from being replayed into another space. Of concurrent first entries of one id with different commitments, each valid when written, the first in the order creates the person key and the others are rejected with the reason "commitment" at their place in the order. A person-key entry that an accepted shred of its id did not see is rejected with "shredded", naming that shred. The state keeps, per person key, every record its accepted entries announce, not only the newest, because concurrent re-wraps have no single newest and the relay must match a record to any announcing entry. An accepted shred always keeps its person-key id in the state, with the shred, even when no accepted entry of the id is left: its entries can lose on their commitment to a concurrent first entry that the shred then rejects, and the erasure must still hold, so the commitment is then none and the relay accepts no record of the id.
- Instead of: a record hash over the whole encoded record, which would make the hash depend on the signature; a record signature without the space id; or keeping one "newest" record by order, which would make the relay refuse a correct re-wrap that lost the order to a concurrent one.
