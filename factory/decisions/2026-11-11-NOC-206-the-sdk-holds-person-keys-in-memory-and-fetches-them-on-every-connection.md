# 2026-11-11 · NOC-206 · The SDK holds person keys in memory, fetches the records on every connection, and puts them after their entries

- Decided by: coding agent (NOC-206, part 2)
- Why: RFC 0003 and RFC 0007 give the person-key store at the relay, the record and the checks a member makes, but not when a member reads or writes the store. The session puts the records a member wrote after it pushed the space's changes, since the relay accepts a record only once its log holds the entry that announces it, and fetches a space's records when it syncs a space whose log names a person key. A member holds a person key only from a record whose writer, current or former, signed it; whose generation and record hash an accepted person-key entry announces; whose key was not shredded; that unwraps under that generation's key; and whose key matches the commitment in the log. The held keys stay in memory, on the space's state, and a member fetches them again on every connection. A put the relay refuses with `bad_record` is dropped whole, since the relay stores none of its records; any other failure keeps it for the next connection.
- Instead of: keeping person keys on the device, which RFC 0003 names ("in its local keystore") but no RFC lays out, so it is an on-disk and key-handling question for the owner; fetching the records only once, which would miss a record another member re-wraps while this one is connected; putting a record before its entry is pushed, which the relay refuses.
- What this does not do: a record that fails is ignored without naming its writer, which RFC 0003 asks the SDK to report; a report needs a public name, which waits for the owner. A record re-wrapped by another member while this one stays connected is fetched only on the next connection. The rotation does not re-wrap records yet (part 3).
