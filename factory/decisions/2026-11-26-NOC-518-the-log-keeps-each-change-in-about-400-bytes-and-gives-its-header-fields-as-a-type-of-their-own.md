# 2026-11-26 · NOC-518 · The log keeps each change in about 400 bytes, and gives its header fields as `HeaderFields`, not as a `Header`

- Decided by: coding agent (NOC-518)
- Why: after NOC-452 the log still kept about 1.4 KB per change, most of an open space's memory when each change holds one record: 120 MB at 81,000 such changes. The bookkeeping now keeps per change: an entry of about 150 bytes with the header's fields besides the payload and unknown keys, its author as a number into a table of the log's authors, and the change itself only until it is released; the entries in chunks of 1,024, so a long log holds at most one chunk of unused room; an author's sequences from 1 up to the first gap as a list of positions, with only the sequences after a gap and the later changes of an equivocation in maps; and one node per change among the tips' heads, with its dependencies as a slice and its clock, in place of a set, a count and a clock in three maps. `crates/nocentraldb/tests/memory_log.rs` holds a reopened space of one-record changes at most 600 bytes per change, and a later change to the log keeps it there. `Log::header` is replaced by `Log::fields`, which returns a `change::HeaderFields` built from the entry: the header's fields without payload and unknown keys, as a type of its own, so that no caller hashes, verifies, re-encodes or compares a partial `Header` and gets a wrong answer without an error. `Checks::may_unfold` takes it, and the membership verdict takes it or a `Header`. A pass that needs the payload or the unknown keys reads the change.
- Instead of: keeping a whole `Header` per entry, so that `Log::header` could still lend one with its unknown keys, about 140 bytes more per change that no pass reads; or a `Header` built from the entry with an empty payload, which looks like the change's header and is not; or indexed columns in the `log` table, so that the bookkeeping leaves memory: an on-disk format change, the owner's question in NOC-521.
- What this does not do: the memory of an open space still grows with its number of changes, by about 400 bytes each.
- Topics: core, memory, performance
