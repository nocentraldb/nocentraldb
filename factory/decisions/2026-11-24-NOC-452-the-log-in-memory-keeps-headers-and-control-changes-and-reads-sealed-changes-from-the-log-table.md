# 2026-11-24 · NOC-452 · The log in memory keeps headers and control changes, and reads sealed changes back from the log table

- Decided by: coding agent (NOC-452)
- Why: the core's `Log` kept every change of every open space, frame and payload, about twice its ciphertext: 63 MB at the 81,000 records of docs/bulk-import.md, growing with the log, more than a phone or a browser tab can give a long-lived space. What the log must hold in memory is what every write and every received change reads: per change its id, its header without the payload, its state, the relay's answer and when the member wrote it; the positions, the tips, the relay and state counts and the status reports kept beside them (NOC-138, NOC-147, NOC-439); and every control change whole, since the membership checks fold all of them and a control change is small. A sealed change's bytes are released once the view's `log` table holds its frame (`Log::release`), and a pass that needs them reads the change back through `log::Frames`, one at a time: checking a rejected change again, un-folding, folding a field again, folding what a migration or an upgrade un-parks, the later edits and conflicts of moves, `newest_model`, the tips once after a reopen, and a rebuild or refold of the view. A `Fold` is the frames of the store it folds into (`Fold::stored`), and the view gives `View::stored_frames` for a pass outside a fold. Un-folding runs whenever a control change passes, so it reads only the changes whose header `Checks::may_unfold` names: those whose author the control state no longer admits, or whose generation's key was replaced or is not held. A pass over sealed changes added later follows the same rule: it reads them through `Frames` one at a time and never holds them all. `crates/nocentraldb/tests/memory_log.rs` holds the heap of an open space below a twentieth of its change bytes, after writes and after a reopen.
- Instead of: indexed columns for author, sequence and kind in the `log` table, so that the per-change bookkeeping could leave memory too: an on-disk format change, the owner's; or a cache of recent sealed changes, which no pass needs, since every pass reads each change once.
- What this does not do: the memory of an open space still grows with its number of changes, by about 1.5 KB each for the header, the state and the bookkeeping beside them (positions, sequences, the tips' dependencies and clocks), and with its control changes. At 81,000 records written 500 to a change that is 0.2 MB; written one to a change, 120 MB. A view still reads every frame once when it opens.
