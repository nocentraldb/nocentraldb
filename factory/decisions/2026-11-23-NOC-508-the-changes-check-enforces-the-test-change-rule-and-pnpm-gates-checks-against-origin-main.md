# 2026-11-23 · NOC-508 · The `changes` check enforces the test-change rule, and `pnpm gates` checks it against origin/main

- Decided by: proposed by the coding agent (NOC-508); the owner decides with the tick on its pull request, a gate change
- Why: the rule needs the pull request's base and its commits, and CI's `gates` job checks out shallow on purpose (ci.yml). So the `changes` check, which already fetches the full history and gets the base and head with the event, runs `check-test-changes.mjs --base --head` as its last step, after a failed step too, and no label waives it. In `pnpm gates` the task `repo:test-changes` compares `HEAD` with `origin/main`, so an agent sees a finding before it pushes; a checkout without `origin/main`, such as the shallow `gates` job, compares nothing and says so. Only the pull request's own commits (`base..head`) count for the trailer, never a commit of `main` merged into the branch. Tests are compared by name and assertions by their text over all changed files at once, so a test or an assertion moved to another file or only reformatted passes, while a renamed test or a rewritten assertion is flagged and needs a reason. Run over the last 80 pull requests merged to `main`, it flagged 27, each a real removal or changed expectation, most of them in tests that read the RFCs' and the site's texts.
- Instead of: a full-history checkout in the `gates` job, which would slow every CI run for one check; or matching tests by count, which would let a deleted test hide behind an added one.
- Topics: gates, ci, tests
