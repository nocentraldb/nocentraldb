# 2026-11-09 · NOC-69 · The view's objects, columns and model until model.lock.json is read

- Decided by: coding agent (NOC-69)
- Why: RFC 0006 leaves the layout internal (decision 2), so these are the core's choices. An object's creates and deletes are its merge state, kept in one `objects` table per database, since an object's collection is itself a merged value; a create into a collection, or a field write, gives the object a row in `c_<collection>`. A basic value or a link has a column (TEXT, INTEGER, REAL or BLOB); a set or links has none, as RFC 0006 allows, and is read from `fs_<collection>`. A column holds NULL when the field is cleared or its winning value is outside the reader's schema; the value stays readable in the merge state. Until the core reads `model.lock.json` (RFC 0005), the view takes `view::Model`: collections with their field types, and indexes with their keys, directions and equality prefix. Its SHA-256 over canonical CBOR is the model hash in `meta` and in a cursor. A database whose format version or model hash differs is refused with an error; rebuilding and additive model changes are later tickets.
- Instead of: an object row per collection in each `c_<collection>` (the collection would have to be decided before the creates converge); reading model.lock.json here, which a sibling ticket builds.
- Topics: rfc-0005, rfc-0006, view, model
