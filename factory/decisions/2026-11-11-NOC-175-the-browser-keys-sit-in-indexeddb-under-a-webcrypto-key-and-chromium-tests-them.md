# 2026-11-11 · NOC-175 · The browser keys sit in IndexedDB under a WebCrypto key, and Chromium tests them in browser-view.yml

- Decided by: coding agent (NOC-175 slice 2), on the owner's NOC-210 A, A, A; the record keys and the fail-closed rule confirmed by pm
- Why: NOC-210 Q1 A gives the IndexedDB database `nocentraldb/<name>`, the object store `keys`, a non-extractable AES-GCM-256 wrapping key, the sealed 113-byte key record (12-byte random IV, ciphertext and tag) and its associated data `"nocentraldb/browser-key-record"` || database name, but not the keys of the two records. They are `wrapping-key` and `key-record`. An open with neither record draws keys and adds both in one transaction, with `add`, so keys another context kept meanwhile are never overwritten. An open with only one, or a record that does not open to a key record of this format, fails with `storageFailed` and never draws keys over it, as a keystore entry that is gone does natively. The key handling stays behind a small seam, `Records`, so the gates test the seal and the open rules in Node through WebCrypto with an in-memory store; Node has no IndexedDB, so the IndexedDB store's tests are ignored there and run in Chromium. They run in the existing `view` job of browser-view.yml, built on the runner and served in Playwright's image by the pinned wasm-bindgen-test-runner in a dedicated worker (NOC-210 Q3 A), since the shared workflow checks assume one job. `load_or_create(name)` is crate-internal; `OpenOptions` gains nothing.
- Instead of: `put`, which could overwrite keys another tab kept at the same moment; drawing new keys over a record that does not open, which would lose every space of the database; a second job, which the shared workflow checks do not cover; a WebDriver for the browser tests, which Playwright's image does not hold; testing IndexedDB only by hand.
- What this does not do: nothing opens a database at a name on wasm32 yet; the database on OPFS and the browser export call `load_or_create` when they are built (NOC-175, NOC-176). No passkey unlocks the wrapping key. Firefox and WebKit do not run the key tests yet.
