# 2026-11-10 · NOC-153 · The relay core finds who a control change made current by resolving the log before it

- Decided by: coding agent (NOC-153), within RFC 0007's "Subscribe" and decision R13
- Why: RFC 0007 sends `added` to a member that an accepted control change makes current, and leaves to the relay how it finds that member. `Relay::push` now returns `Push { results, added }`: for each accepted control change, the members current in `resolve` over the log's control changes with it and not current without it, each once, in the order they became current. The core already holds the control changes it read for the check, so it runs `resolve` a second time over them instead of reading each member's stored row, which on DynamoDB would cost one read per member of the space. The append is conditional on the head both results were computed at, so the answer is exact. A genesis makes its creator current. The server sends `added` to every open connection of each such member, as R13 says, the connection that pushed included (pm, 2026-11-10, on #152): the pushing connection queues it right after `pushed`, since a member that already follows the space has nothing to do; every other connection gets it from the hub, each message waiting for room in its connection's bounded queue on a task of its own, so a slow member never holds up the push that added it.
- Instead of: reading the stored membership row of every member the new table lists, one backend read each; skipping the connection that pushed, which departs from R13's "each of that member's open connections"; or `try_send`, which drops `added` whenever another connection's queue is momentarily full.
- What this does not do: a control change costs a second `resolve` over the space's control changes. A connection that closes before its `added` is written loses it, and its member learns of the space from `welcome` at the next connection, as RFC 0007 says.
