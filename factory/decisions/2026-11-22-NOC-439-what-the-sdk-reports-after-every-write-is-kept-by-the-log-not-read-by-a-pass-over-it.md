# 2026-11-22 · NOC-439 · What the SDK reports after every write is kept by the log as changes arrive, never read by a pass over the log or a scan of the log table

- Decided by: coding agent (NOC-439)
- Why: the SDK reads every followed report again after every write, and the TypeScript SDK follows the status of each space it holds a handle on and the durability report. A space's status went through every change of its log for `refused`, `equivocations` and `newestModel`, and the durability report's `oldestUnconfirmedAt` ran `SELECT MIN(written_at) FROM log`, which no index serves. So every write cost a pass over the log, and a one-object write in Chromium went from 6.3 ms at 2,000 objects to 16.4 ms at 30,000. The core's `Log` now keeps the refused positions per author, the author sequences with more than one change, the positions with parked data and the unconfirmed own changes by the time they were written, as it keeps its relay counts (NOC-147) and state counts. Each entry keeps its `written_at` in memory; the view reads it back when it loads the log. A report added later, or a field added to one, follows the same rule: the log or the view keeps it as changes are appended, given states, confirmed and refused, and the read touches only what it returns. `log_status_cost.rs`, `view_oldest_unconfirmed_cost.rs` and the browser test `writeCost.e2e.test.mjs` hold the current reports to it.
- Instead of: a partial SQLite index on `log (written_at) WHERE relay_position IS NULL`, an on-disk format change, which is the owner's; or reading the reports less often, such as once per batch of writes, which would leave a report behind the copy it describes.
- What this does not do: loading the log at open still reads every frame once, as it did. A batch write still costs more per object as the view's tables and indexes grow (274 ms for 1,000 objects at 10,000 objects in Chromium, 620 ms at 100,000), and the profile puts most of the added time in SQLite writing pages to OPFS, not in a pass over the log.
