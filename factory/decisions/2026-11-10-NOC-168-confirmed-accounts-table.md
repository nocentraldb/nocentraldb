# 2026-11-10 · NOC-168 · The database keeps confirmed accounts in `confirmed_accounts`, beside the view, and the view format version stays 2

- Decided by: the owner on what is kept (Carsten, 2026-11-10, NOC-154 point 3 A); the layout and where it lives by the coding agent (NOC-168), for pm and the owner to check in the PR
- Why: the owner decided that the database remembers each account whose fingerprint a person confirmed, in a new table of its SQLite file, holding the account's public key and when it was confirmed. The table is `confirmed_accounts (account_key BLOB PRIMARY KEY NOT NULL, confirmed_at INTEGER NOT NULL) STRICT`: the account's 32-byte Ed25519 public key, and the time of the first confirmation in milliseconds since the Unix epoch, from the device's wall clock. A second confirmation keeps the first time. It lives in `ncdb-core`'s view module, because the view holds the file's one SQLite connection and its `meta`, but it is no part of the view: no fold computes it, so folding the log again leaves it alone, and a future rebuild of the view must keep it like `log`. It is created with `CREATE TABLE IF NOT EXISTS` on every open, so a database from before gains it, empty, and a core that does not know it ignores it. Like the stored lock (RFC 0006, decision 17), it breaks no reader, so the view format version stays 2. `members().add` records the account only after the add is written and folded; a refused add records nothing, and the database's own account is never recorded. A confirmed account is known by its key, so a fingerprint passed with it is not compared again.
- Instead of: raising the view format version to 3, which would make every older core refuse the file although nothing in it changed for that core; keeping the table in the SDK on a second SQLite connection, which would give the file a second writer and a second version; keeping the fingerprint instead of the key, which RFC 0010 will compute over the recovery key; seconds instead of milliseconds, which the clock of a change counts in.
- What this does not do: the confirmation is written in its own transaction after the add's changes, so a crash between them loses it and the next add asks for the fingerprint again. Nothing lists or forgets a confirmed account yet, and the browser's view (OPFS) does not exist yet. RFC 0009 and RFC 0006 do not record the table yet; pm records it there once the owner approved the layout.
