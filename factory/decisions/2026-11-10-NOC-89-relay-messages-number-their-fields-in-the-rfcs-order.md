# 2026-11-10 · NOC-89 · Relay messages number their fields in RFC 0007's order, after the type and the request id

- Decided by: coding agent (NOC-89); a wire-format detail GENESIS.md reserves for the owner, named in the PR for the owner to confirm
- Why: RFC 0007 fixes only key 1 (the type, as text), key 2 (the request id) and the error map `{1: "error", 2: req, 3: code, 4: retry after}`. The server follows that example as the rule: key 2 is absent when a message has no request id (`hello`, `challenge`, `auth`, `welcome`, live `entries`); every other field sits at keys 3, 4, ... in the order the RFC lists it; a nested map numbers its fields from 1 in the RFC's order; types and error codes are text. So `hello {3: versions, 4: client}`, `challenge {3: version, 4: relay id, 5: nonce, 6: limits {1: largest message, 2: frames per push, 3: largest frame}}`, `auth {3: signing key, 4: agreement key, 5: signature}`, `welcome {3: member id, 4: relay epoch, 5: spaces}`, `push {2: req, 3: space, 4: frames}` with an upload reference `{1: upload id}`, `pushed {2: req, 3: results}` with `{1: position}` accepted, `{2: position}` duplicate, `{3: code}` rejected, `pull {2: req, 3: space, 4: epoch, 5: after, 6: limit}`, `entries {2: req, 3: space, 4: entries, 5: head}` with an entry `{1: position, 2: accepted at, 3: frame}`, `subscribe {2: req, 3: space, 4: epoch, 5: after}`, `unsubscribe {2: req, 3: space}`, `upload {2: req, 3: space, 4: size}`, `keys` and `person-keys {2: req, 3: space}`, `put-person-keys {2: req, 3: space, 4: records}`, `ping` and `pong {2: req}`. A request with a key its type does not define is `malformed`: a new field comes with a new protocol version, which `hello` negotiates.
- Instead of: text keys named after the RFC's fields, which cost bytes in every message; or a numbering of our own that a reader cannot derive from the RFC.
