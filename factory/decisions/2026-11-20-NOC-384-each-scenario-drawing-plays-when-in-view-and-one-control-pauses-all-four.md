# 2026-11-20 · NOC-384 · Each scenario drawing plays when an IntersectionObserver sees it, and one pause control per figure holds all four

- Decided by: coding agent, NOC-384 (for pm's review)
- Why: the wide drawings carry their SMIL loops again, as the hero's does (scene.mjs loses its `still` option, which nothing draws any more). `site/src/components/story-motion.mjs` holds each drawing at the start of its loop until an IntersectionObserver reports it in view, then lets it play; out of view it holds where it is and plays on when it comes back, so a drawing is never set back or moved by the scroll, and no drawing off the screen runs. Nothing reads the scroll position. Under reduced motion (and in a screenshot, `?shot`) every drawing holds 0.72 s into its loop, the picture NOC-380's still drawing showed. Each figure has a Pause button at its bottom right, the hero's control in look and name (`aria-label="Pause the animation"`, `aria-pressed`), so a reader finds one beside the drawing that moves; any of them holds or releases all four. The buttons are `data-story-pause`, not the hero's `data-scene-pause`, so the hero's scene-pause.mjs (shared with NOC-360's work) stays untouched and does not start the scenario's drawings on load. The markup carries them hidden: without script none stands dead, and the drawings loop as SVG does. The phone schematic stays still (the ticket allows its cue to move; it was left still to keep this PR to the restoration), and below 640 px no control shows.
- Instead of: one control for the whole scenario above its steps, out of reach while reading step 4; sharing the hero's control, which is off the screen in the scenario and hidden on a phone; starting every drawing on load, which runs drawings nobody sees and starts each one mid-loop; restarting a drawing from its start each time it comes back into view, which ties how far it has played to the scroll.
