# 2026-11-15 · NOC-329 · Every developer-facing text lives in texts/texts.json, which generates the SDKs' text modules

- Decided by: Carsten, 2026-11-15, on NOC-329 (one place for every text, each with when it shows, reviewed before each beta and stable release); pm, NOC-329, on the coding agent's proposal (the format, the place, the scope and the order)
- Why: a text a developer reads should be found, read and reviewed in one place, with when it shows, not worked out from the code. `texts/texts.json` holds one entry per text: `id` (`<kind>.<code>`), `kind`, `code` as RFC 0009 spells it, and `text`, and `when` it shows. What changed since the last release comes from git (see the decision on the review from git diff). `scripts/texts.mjs` generates `crates/nocentraldb/src/texts.rs` from it, committed and compared byte for byte by the gate `repo:texts`, which also fails on a notice text written in the SDK's code and on a text no code uses. The TypeScript SDK receives the notices through the bridge. RFC 0009 keeps the codes; the texts it quotes are copies, and a test holds them equal to the file. Slice T1 moves the eleven notices; T2 the Rust SDK's error messages; T3 the TypeScript SDK's own texts, after NOC-316; T4 `pnpm texts`, which lists every text new, changed or removed since the last release tag from `git diff`, and its step in docs/release-management.md; T5 the `ncdb` CLI's messages. The relay's error codes stay out: they are machine codes.
- Instead of: TOML, which the TypeScript SDK would need a parser for; a `build.rs` in the Rust SDK that reads JSON, which needs a build dependency and so a change to `Cargo.lock`, and the wasm build with it; or one Rust module the bridge passes through, which leaves the TypeScript SDK's own texts outside.
