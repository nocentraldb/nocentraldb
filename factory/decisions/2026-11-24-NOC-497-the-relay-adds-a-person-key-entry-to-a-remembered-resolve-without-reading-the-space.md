# 2026-11-24 · NOC-497 · The relay adds a person-key entry to a remembered space's resolve without reading the space

- Decided by: coding agent (NOC-497)
- Why: a warm push still called `Resolver::resolve` over every control change of the space, which rebuilds the resolver's input from each of them, and the put after it did so again: about 61 ms each at 10,000 persons. `membership::Resolver` now keeps the input and judgements of its last call while its running fold covers every node, and `Resolver::add` judges a person-key entry whose causal past is exactly that set and adds it to the input and the fold, as `resolve` would; it refuses anything else, and the caller resolves the whole set. The relay calls `add` first and keeps the change it appended in the space's memory. A warm push of a person-key entry now costs about 3 ms at 10,000 persons and its put 0.4 ms; what still grows is a copy of the control state that `add` returns. Keeping the last input raises a remembered space to about 8.8 KiB per control change (85 MiB at 10,000), and a cold request on it allocates at most about 93 MiB at once, measured natively on Linux; NOC-492's bound of 16 spaces and 10,240 control changes over all of them stands, and with one request's work now takes about 181 MiB of a 256 MB Lambda instead of 185 MiB. `add` must give `resolve`'s state: the convergence harness checks it against `Resolver::from_scratch`, so any change to steps 1 to 5 must keep `add` equal to them.
- Instead of: making `resolve` find on its own that its set grew (still a read of every change), or keeping no input and rebuilding it on each push (the linear cost this ticket measured)
