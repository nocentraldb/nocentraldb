# 2026-11-20 · NOC-376 · Only publish-crates and publish-npm run in the environment registry-publish, which crates.io names and npm's trusted publisher does not

- Decided by: the owner chose option A on NOC-376 (Carsten, 2026-11-20): a GitHub environment that crates.io's and npm's trusted publishers name, set on exactly the jobs that publish. The coding agent (NOC-376) decided the npm part below, for the owner's review on the PR.
- Why: with trusted publishers that name no environment, every job of `release.yml` holding `id-token: write` could obtain a registry token, among them `alpha-npm`, which builds `main`'s code after every merge. `publish-crates` and `publish-npm` now carry `environment: registry-publish`, and no other job does; the contract test fails when a job holds `id-token: write` outside the environment, other than `alpha-npm`, or when a registry job leaves it. crates.io's trusted publisher of each of the four crates names the environment, so only those two jobs can obtain a crates.io token. npm's trusted publisher of `@nocentraldb/sdk` stays without an environment: npm knows one trusted publisher per package, and `alpha-npm` publishes every alpha through it directly (Carsten, 2026-11-16, NOC-346). Naming the environment there would stop the alphas; putting `alpha-npm` into the environment would hand it crates.io tokens again, and a `v*` tag rule on the environment would refuse it, since it runs on `main`. Betas and releases reach npm only staged, public after the owner's 2FA approval, so the environment adds little there. `publish-npm` still runs in the environment, so a required reviewer or a tag rule holds it back with `publish-crates`.
- Instead of: naming the environment in npm's trusted publisher too, which stops the alphas on npm; giving `alpha-npm` the environment, which undoes the point of it for crates.io; a second environment for the alphas, which npm's single trusted publisher per package cannot name alongside the first.
