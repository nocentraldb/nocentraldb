# 2026-11-13 · NOC-303 · Token URLs are a second backend trait, and the AWS backend keeps no tokens table

- Decided by: pm, on NOC-303, following the owner's NOC-295 A (Carsten, 2026-11-13: remove the unused `tokens` table before the first deploy)
- Why: Behind API Gateway the URLs of large changes are presigned S3 URLs, so the AWS backend serves no URLs of its own and its `tokens` table was unused. But the relay core's backend interface, `RelayStore`, carried the four methods that only token URLs need (`upload` by token, `fill_upload`, `begin_download`, `download`), and the conformance suite tested them on every backend. They now form a second trait, `TokenUrls: RelayStore`. SQLite implements it, and the relay server, the local harness and the core's `TokenDownloads` require it; `AwsStore` implements only `RelayStore`. Its `begin_upload` writes only the upload item, and `take_upload` takes an upload whose S3 object holds exactly the declared size. The four conformance rules that use a token move into `token_urls_conformance_suite!`, which SQLite runs next to `conformance_suite!`: SQLite runs 22 rules as before (18 + 4), and AWS runs every rule it ran before except the four token rules, 18 of 22. No rule is deleted or loosened. The Lambda crate's `Urls` becomes generic over the backend, so the harness's URLs require `TokenUrls` and S3's take any backend. The CDK stack and the backend's schema code no longer create `tokens`, and RFC 0007 shows the second trait and drops the table.
- Instead of: keeping `RelayStore` whole and having `AwsStore` answer the four token methods with an error, with a per-backend opt-out for their tests in the conformance suite, which is a run-time failure and a gate change; or keeping the tokens inside `uploads`, which has no place for download tokens and is no removal.
- Topics: relay, aws, backend, conformance, tokens
