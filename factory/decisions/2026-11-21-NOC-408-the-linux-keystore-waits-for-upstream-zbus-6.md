# 2026-11-21 · NOC-408 · The Linux keystore waits for upstream's move to zbus 6

- Decided by: Carsten, 2026-11-21, in chat with pm ("Ich folge deiner Empfehlung"), on pm's recommendation
- Why: `nocentraldb` keeps its keys on Linux through `zbus-secret-service-keyring-store` 1.0.1, whose tree pulls zbus 5. RUSTSEC-2026-0370, -0371 and -0372 mark `zvariant`, `zbus_names` and `zvariant_derive` 5.x as unmaintained, so an embedder running cargo-deny with `unmaintained = "deny"` goes red. No release of the store or of `secret-service` is on zbus 6 yet; only `secret-service` 6.0.0-rc.1 exists, and upstream's draft PR open-source-cooperative/zbus-secret-service-keyring-store#39 does the move without changing the entry format decided in NOC-144. The advisories report unmaintained crates, not a vulnerability, and the one embedder affected, nexus-flow, carries dated exceptions until 2027-02-21. So the fix ships in the first beta after `secret-service` 6.0.0 and a store release on it are out, as a version bump checked with cargo-deny. If nothing is released by 2027-01-15, the fallback is to pin `secret-service =6.0.0-rc.1` and carry #39's adapter ourselves. pm checks upstream weekly.
- Instead of: shipping the fix in 0.1.0-beta.2, decided earlier the same day; switching to `dbus-secret-service-keyring-store`, which needs the system libdbus at build time and stays rejected as in NOC-108; pinning the release candidate now, which puts a pre-release dependency and ~300 lines of adapter into key handling; writing our own zbus 6 Secret Service client.
- Topics: dependencies, keystore, security-advisories, release
