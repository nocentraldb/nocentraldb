# 2026-11-11 · NOC-198 · Shred stability takes the holder's runs from the caller, and counts every member with an admin grant

- Decided by: coding agent (NOC-198), inside the core, with pm (plan confirmed 2026-11-10)
- Why: RFC 0008 ("When a change is stable") counts "every change of that member from author sequence 1", sealed changes too, but `resolve` sees only control changes. `Resolved::stability(changes, held)` therefore takes `held(m)`, the highest n such that the holder holds m's changes 1 to n, from the caller: the view's log on a member, the relay's log for NOC-113. Where the RFC leaves the reading open, the core takes the side that never lets a key be destroyed too early: "held the admin role" counts every member with an accepted grant of admin, a lost one included; a revocation bounds a member's run only while that member does not hold admin now, so a re-granted admin must write after the change; and a member's own change must have the change in its causal past, so the shred's author is not satisfied by the shred itself. Stability is computed for every accepted control change, as the rule needs stable revocations, and blocking members are reported per accepted shred.
- Instead of: runs counted over control changes only, which the RFC's rule does not allow, since it counts every change of the member; counting only members whose effective role reached admin, which a lost raise on another island could make wrong.
- Topics: membership, rfc-0008, erasure
