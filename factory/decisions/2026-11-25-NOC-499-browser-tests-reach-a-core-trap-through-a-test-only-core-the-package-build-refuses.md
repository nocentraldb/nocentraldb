# 2026-11-25 · NOC-499 · Browser tests reach a real core trap through a core built with the feature `test-trap`, which the package's build refuses to ship

- Decided by: pm (option A on NOC-499), built by the coding agent of NOC-499
- Why: a write large enough to run the core out of memory runs the page out of its own memory first on some machines (a `RangeError` in CI at 1.25 GiB, NOC-522), and a write of 2 GiB got no answer in Chromium (NOC-523), so a trap reached by size depends on the machine and on the core's memory use. A core built with the feature `test-trap` of nocentraldb-wasm traps with WebAssembly's `unreachable`, as an allocation failure does, while it answers a request that holds the marker `nocentraldb:test-trap` (packages/sdk/testTrap.mjs). scripts/sdk-browser/trap.mjs builds it in a target directory of its own into a copy of the package, which only trap.e2e.test.mjs loads; browser-view.yml builds it after the package. The feature is off by default, packages/sdk/build.mjs refuses a module that holds the marker, and the trap test checks the built package's module, so the package never ships it.
- Instead of: growing a write until the core runs out of memory, toward wasm32's 4 GiB ceiling, which the page's memory does not reach; a bridge call `debugTrap`, which the SDK has no way to send from a page.
