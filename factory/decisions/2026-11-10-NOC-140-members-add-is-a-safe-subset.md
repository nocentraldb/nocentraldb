# 2026-11-10 · NOC-140 · `members().add` returns nothing, knows only the database's own account, and refuses what RFC 0009 names no code for with `InvalidValue`

- Decided by: coding agent (NOC-140), the safe subset; the names are the owner's (Carsten, 2026-11-10, NOC-135 A)
- Why: the owner decided `db.invitation() -> Invitation`, `space.members() -> Members`, `Members::add(&Invitation, AddMember) -> Result<()>`, `AddMember { role: Role, fingerprint: Option<Fingerprint> }` and `Role::{Reader, Writer, Admin}`. RFC 0009 has `add` return a notice `{ code, text }`, but names no code for it and no Rust type, so `add` returns `()` as decided. RFC 0009 leaves open which accounts a device knows; the SDK knows only the database's own account, since each database draws its own (S20), and keeps no record of fingerprints a person compared, which would add to the on-disk format. A fingerprint that is not the invitation's is refused like none, with `UnknownAccount`. RFC 0009's error table names `notAllowed` and `notMember` for membership calls, which `add` uses for a member that is no admin or was removed, but no code for a certificate that does not hold, for adding a member twice, or for adding a removed member again without the rotation RFC 0008 asks for (M5); each is refused with `InvalidValue`, before anything is written. A sub-agent's certificate is refused too, since its parent signs it when it is added (M25), which is not built. The entry depends on the heads of the control DAG only (RFC 0008, "Terms").
- Instead of: writing an entry the fold rejects, which the relay and every member would then refuse; a notice type whose Rust name nobody decided; trusting any account a space already holds.
- What this does not do: `Invitation` and `Fingerprint` have no text form, so a person cannot compare a fingerprint on screen yet and the invitation does not leave the process (NOC-141). `UnknownAccount` names no fingerprint, since `Error` has no field for one. A confirmed fingerprint is not remembered, so every add of a member of another account passes it again. `add` takes one invitation, not a list, and `role` is required, also for an agent (RFC 0008, M14). `list`, `set_role` and `remove` are follow-ups. A connected member learns that it was added only when it connects again (NOC-143).
