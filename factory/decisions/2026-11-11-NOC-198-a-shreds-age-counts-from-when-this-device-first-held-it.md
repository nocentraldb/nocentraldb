# 2026-11-11 · NOC-198 · A shred's age counts from when this device first held it, which a table beside the view keeps

- Decided by: the owner, NOC-218 A, A, A (2026-11-11), for the age, the blocking accounts and when they show; the coding agent (NOC-198) for the core additions, which pm approved
- Why: RFC 0009 gives `ShredWaiting { change, age, blocking }`, and RFC 0008 says the alarm names "the shred's age", but not from when. A control change carries no clock (RFC 0008, "The control bodies"), and the relay sends no time of acceptance (RFC 0007). So the age counts from when this device first held the shred, by its own clock. The table `shreds_held (space_id, change_id, held_at)` keeps it, beside the view like `confirmed_accounts`, so a restart keeps the age and a rebuild does not touch it. The SDK notes every accepted shred after it folds changes, and when it opens a database, for shreds held before the table existed. `blocking` names each blocking member's account by `Fingerprint` over its certificate's account key, each account once, in key order. It is filled only when this device is an admin of the space and the shred waited 7 days; otherwise it is empty. The core computes the runs (`Log::runs`, from the index of author and sequence) and the stability over the checks' control changes (`SealChecks::stability`).
- Instead of: the shred's own clock, which control changes do not carry; an age kept in memory since the database opened, which a phone's restarts would keep below 7 days; the relay's time of acceptance, which RFC 0007 does not send; blocking named per device, which needs a public member id the owner left out of v1 (NOC-193).
- What this does not do: a device that joins later, or a fresh install, starts the age at 0, so its alarm comes late, never early. The status computes stability on each read while a shred is accepted; a space without one costs nothing.
