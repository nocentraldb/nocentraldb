# 2026-11-23 · NOC-479 · A change at the 16 MiB limit fits in 256 MiB of core memory, natively and in a browser tab's WebAssembly memory

- Decided by: Carsten (2026-11-23, NOC-451, question 1 A)
- Why: GENESIS promises the same core on any device, and a stated budget makes that checkable: a developer can plan a tab or a smaller device against it. After NOC-422, one change of 15.5 MB peaked at 231 MB on the writer and 161 MB on a receiver natively, and at 191 MiB of WebAssembly memory in a Chromium tab. A guard test keeps the budget: natively, the peak resident memory of the writing and of the receiving device's process, SQLite included (crates/nocentraldb/tests/memory_budget.rs); in Chromium, the WebAssembly memory of the core in the writing and in the receiving tab (scripts/memory-budget/browser.test.mjs). Each writes and receives one change just below 16 MiB and fails above 256 MiB. The budget binds every later change to the core: a change that breaks it lowers the memory again or comes back to the owner.
- Instead of: stating only the measurements, which costs nothing but gives a developer nothing to plan a phone or a tab against.
- What this does not do: a phone was not measured; the budget rests on native and Chromium. In a tab it covers the core's WebAssembly memory, not the page's own copy of the records or the browser. The guard runs only for releases (Carsten, 2026-11-23, NOC-451): in the release workflow's `verify` job for beta and stable tags and in the publish dry run, never in PR CI, so a change that breaks the budget shows when a release is cut, not when it merges.
