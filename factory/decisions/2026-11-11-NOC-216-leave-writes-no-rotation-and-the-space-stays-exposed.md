# 2026-11-11 · NOC-216 · `space.leave()` writes no rotation, and the space stays exposed until an admin rotates

- Decided by: coding agent (NOC-216), within pm's scope (2026-11-11: NOC-216 is leave() alone; the admin's automatic rotation is NOC-220)
- Why: RFC 0008 has a member that leaves name its own highest sequence as the cutoff and not rotate, "because it must not know the next key, so the next admin that sees the removal rotates for it". So `leave()` writes only the removal, with `Tips::next_sequence - 1` of its own member as the cutoff, in one batch. The space's current generation is then one the leaver holds, so RFC 0008's exposure rule marks it exposed, and `space.status()` says so on every member that folded the leave, which a test checks. The SDK does not yet write the merge rotation on its own when it sees an exposed current generation; until NOC-220 builds that, an admin's next `remove`, `set_role` re-grant or re-add rotates, and the `SpaceLeft` notice names the limit (Carsten, 2026-11-11, NOC-219). Any member may leave, a reader included; the last admin is refused with `LastAdmin`, counted in the copy's own membership state, so two admins leaving at once can still leave the space without one, as RFC 0008 accepts.
- Instead of: the leaver rotating, which would hand it the next key; building the admin's automatic rotation into this ticket, which lives in `sync/` and is NOC-220.
- What this does not do: it does not rotate for the leaver, and it does not keep two admins from leaving at the same time.
- Topics: sdk-rust, rfc-0008, members, rotation
