# 2026-11-09 · NOC-64 · The owner decides RFC 0009, the SDK API, S1 to S18 as recommended

- Decided by: Carsten, 2026-11-09, in chat with pm, on #78
- Why: the SDK opens with `nc.open({ model, lock, relay })`; single objects are read and written through a space handle, and queries run through `db.find` across spaces; `space.write(tx => ...)` records one change and resolves when it is folded on the device; sets and links take `nc.add` and `nc.remove`; reads are plain `nc.Infer` objects with `$`-properties and `nc.Unknown`, details in `space.inspect`, with RFC 0004's working names as public names; queries use index handles with `.equal`, `.take` and `.after`, an index option `scope: "space"` and `space.find`, and skip deleted objects; subscriptions pass the whole page; spaces have no name in the SDK; a joining member's invitation is its public identity; the roles are reader, writer and admin; no group object in v1; account entry points are named only; one relay per database; one `nc.Error` with string codes; the Rust SDK has the same calls in snake case, fields by name.
- Instead of: the alternatives each decision S1 to S18 of RFC 0009 lists, among them a lock-only open (S1 B), wrapped fields in every read (S5 B), whole-array set writes (S4 B), a reserved `$space` collection for names (S11 B), two-hop or relay-carried invitations (S12 B, C), and typed Rust structs in v1 (S18 B).
