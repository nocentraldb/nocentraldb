# 2026-11-09 · NOC-56 · commit-back pushes to main with a release GitHub App's token, which the ruleset's bypass lets through

- Decided by: pm, after the owner found that the ruleset's bypass list does not offer the GitHub Actions app and created an organization GitHub App for the release push; the bypass, the app and its key are owner settings
- Why: the ruleset "Require PR" on `main` refuses a direct push. The release commit stays a direct push, with no extra pull request per beta or release waiting for the owner's review, by pushing as an app that is the only actor on the bypass list. `commit-back` mints a token for it with `actions/create-github-app-token`, pinned by SHA, from `vars.RELEASE_APP_ID` and `secrets.RELEASE_APP_PRIVATE_KEY`, narrowed to contents: write; the token lives an hour at most. The job's own `github.token` drops to read-only, and no other job mints the token, which `scripts/release-ruleset.test.mjs` holds. Unlike a bypass for every workflow token, a workflow that pushes with `github.token` stays refused. The app's private key is the one long-lived secret this adds; the runbook says so and how to rotate it. The app's push starts `ci` on `main`, so the gate also runs on the release commit.
- Instead of: a bypass for the GitHub Actions app, which the bypass list does not offer and which would let every workflow token with contents: write past the ruleset; commit-back opening a pull request, which needs the owner to let GitHub Actions create pull requests and whose pull request, opened with the job's token, would never run the required checks; or a deploy key as the bypass actor, a long-lived key that pushes directly without a short-lived token in between.
