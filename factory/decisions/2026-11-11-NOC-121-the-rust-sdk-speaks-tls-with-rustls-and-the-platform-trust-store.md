# 2026-11-11 · NOC-121 · The Rust SDK speaks TLS with rustls on ring and verifies the relay against the platform's trust store

- Decided by: coding agent (NOC-121, second part), on pm's plan (one platform-trust crate, named for the owner's tick)
- Why: RFC 0007 requires TLS on every connection. The Rust SDK now opens `wss://` relays and fetches `https://` upload and download URLs, with one rustls client configuration for both. New direct dependencies, each pinned: `rustls` 0.23.46 with the `ring` provider (pure Rust and assembly, built with a C compiler only, no cmake as `aws-lc-rs` needs), `tokio-rustls` 0.26.6 for the HTTP client, `rustls-native-certs` 0.8.5 as the one platform-trust crate, and tokio-tungstenite's `rustls-tls-native-roots` feature for the WebSocket. `rustls-native-certs` reads the platform's root certificates (the Keychain on macOS, the system store on Windows, the CA bundle on Linux) into rustls's own verifier; it is the trust store tokio-tungstenite's own feature uses, and it adds few crates. `ws://` and `http://` stay for a relay on the local network.
- Instead of: `rustls-platform-verifier`, which hands verification to the operating system's verifier (revocation, enterprise policy) but pulls in more crates per platform, among them JNI for Android, which this SDK does not target yet; `native-tls`, which links OpenSSL on Linux; `webpki-roots`, a compiled-in copy of Mozilla's roots that ignores the platform's store and goes stale between releases.
- What this does not do: no revocation checks beyond what rustls's verifier does; no certificate pinning; a root added to the platform's store after the process started is read only by a new process.
- Topics: sdk-rust, sync, tls, dependencies
