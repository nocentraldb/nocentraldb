# 2026-11-12 · NOC-272 · The Lambda function runs on the AWS backend and reads its settings from the environment

- Decided by: coding agent (NOC-272), following NOC-264 and pm's plan for NOC-272
- Why: the function now has a backend, a `connections` store and a connection API client, so `main` wires them and starts Lambda's runtime. Its settings come from environment variables the deployment sets: `NCDB_RELAY_ID`, `NCDB_ALLOWED_ACCOUNTS`, `NCDB_TABLE_PREFIX`, `NCDB_BUCKET` and `NCDB_CONNECTIONS_URL`. A missing or malformed one stops it at start and is named, never its value; outside Lambda it says so and exits instead of panicking in the runtime. Its credentials are the function's role, so it holds no key. The AWS parts (the binary, the backend, `connections` on DynamoDB, the connection API, presigned S3 URLs and Lambda's runtime) sit behind the feature `aws`, which the binary requires, so the Rust SDK's sync suite, which runs the handler through the harness, compiles no AWS SDK: with them always on, `pnpm gates` outgrew an agent container's disk (NOC-279).
- Instead of: a configuration file in the function's package, which a deploy would have to rebuild for every setting; or table and bucket names fixed in code, which leave the deployment no room to name them per account and stage.
