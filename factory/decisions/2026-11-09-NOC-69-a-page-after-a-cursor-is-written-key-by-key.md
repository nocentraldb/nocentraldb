# 2026-11-09 · NOC-69 · A page after a cursor is written key by key, and the plan check accepts SEARCH or SCAN on the declared index

- Decided by: pm, on the coding agent's question (option A); the PR goes to the owner because it departs from RFC 0006's written cursor shape and plan check
- Why: RFC 0006's row-value shape `(f, space_id, object_id) > (?, ?, ?)` gives a wrong page in two cases: a cursor whose last row has an unset field (a row-value comparison with NULL is NULL, so the next page is empty although rows follow), and a descending key (row values compare every key one way, and every index ends with ascending `(space_id, object_id)`). The view writes the condition key by key, NULL-aware and per direction, nested so that SQLite walks one index, with a bound on the first key so an ascending page seeks to the cursor; a descending first key scans within the equality prefix. An index without an equality prefix plans its first page as `SCAN ... USING COVERING INDEX`, which reads only the page, so the check on open accepts SEARCH or SCAN on the declared index and refuses any other index and any temporary B-tree.
- Instead of: B, the RFC's row values with ascending indexes only, which leaves a cursor on an unset value broken until the SDK; C, row values where they are correct and this condition otherwise, two code paths now.
