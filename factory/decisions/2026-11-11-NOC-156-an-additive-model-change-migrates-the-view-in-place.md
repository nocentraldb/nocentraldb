# 2026-11-11 · NOC-156 · An additive model change migrates the view in place, and folds only what was parked as unknown

- Decided by: coding agent (NOC-156, part A), on RFC 0006's table in "Rebuilding the view"; pm agreed to split the ticket, so the background rebuild and its progress in `db.view` wait for the owner's answer on NOC-227
- Why: RFC 0006 says an added index is a `CREATE INDEX` with no refold, and an added field or collection adds its column or table and folds the parked operations that are now known, with no full rebuild. The view keeps only the hash of the model its tables were folded by, so the migration runs only when that hash is the stored lock's model and the new model keeps every collection, field and index of it unchanged. `Additions::between` checks that, and `schema::open` answers `Fit::Migrate`. The migration then runs the DDL and updates `meta`. For each space, it reopens only the folded changes with an operation parked as an unknown collection or field. It gives the space's checks the folded control changes and folds those operations through the ordinary `understand` and `fold_one` steps. Each field's state is a function of its set of operations (RFC 0004), so the result equals a full fold under the new model, and a test compares the two. Checks are needed only when something waits to fold, so a migration with nothing parked, or one that only adds an index, opens through `View::open` too.
- Instead of: keeping the full refold for every model change, which blocks `open` for the whole log; diffing the locks without the stored model's hash, which would migrate a view folded by an older lock after a rollback.
- What this does not do: anything that is not purely additive, such as a rollback to an older lock, still folds the whole log again inside `open`; part B moves that to the background. A parked change that no longer opens keeps its parked operations.
