# 2026-11-12 · NOC-237 · An offline write in the example app succeeds on the device and says the relay does not hold it yet

- Decided by: pm, NOC-237, on the coding agent's proposal after running the README's steps against the real binaries
- Why: the example app `tasks` waits after each write until the relay holds it, since the process exits and syncing stops with it. With the relay stopped, that wait could not end: `tasks add` kept the task on the device, then failed after 30 s with "not synced after 30s", while the README promised that each device keeps working on its own copy. The example should teach local-first: an offline write succeeds. So a write (`create`, `add`, `done`, `invite`) that finds the connection offline, with no error from the relay, stops waiting, prints "saved on this device; the relay does not hold it yet, run `tasks sync` when it is back" to stderr and exits 0. Online it still waits for the relay as before. `sync` and `status` still wait, since they exist to report the relay's view. The gate test covers it: with the relay stopped, `add` exits 0 on each device and `list` shows the task; with the relay back on the same database and address, `sync` brings both devices to the same list.
- Instead of: keeping the 30 s timeout and its non-zero exit, which teaches that writing needs the relay; or rewording the README to say offline writes report a timeout, which describes the problem instead of the local-first behaviour the SDK already has.
