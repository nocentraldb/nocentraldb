# 2026-11-19 · NOC-374 · The crates are packaged and built before the crates.io token exists, then published with --no-verify and --allow-dirty

- Decided by: coding agent (NOC-374), for the owner's review on the PR
- Why: crates.io versions are permanent. If the third crate failed cargo's verification after the first two were published, crates.io would hold a partial beta for good. So `publish-crates` first runs `crates-publish.mjs --verify-only`: one `cargo package --locked --allow-dirty` over every missing crate, which packages each one and builds it from its package against the packages of the crates before it (cargo 1.99 resolves a sibling's unpublished version from a local overlay; checked on this repository at `0.1.0-beta.1`, about 90 seconds). Only then does `rust-lang/crates-io-auth-action` fetch the 30-minute token, and each crate is published with `cargo publish --no-verify`, which skips a second build of the same sources. `--allow-dirty` is needed because `set-version` writes the full version into the checkout's manifests; cargo refuses a dirty tree without it (seen locally). The package's `.cargo_vcs_info.json` then records the tagged commit and `dirty: true`, which is true. The order is computed by the script, not left to `cargo publish --workspace`: a crate comes after every published crate it names as a workspace dependency, dev-dependencies included, since crates.io must resolve a dev-dependency that keeps its version (NOC-372). Whether a version is already there is read from the crates.io sparse index, cargo's own protocol (`https://index.crates.io/<prefix>/<name>`), so a re-run publishes only what is missing.
- Instead of: `cargo publish` with its own verification after the token is fetched, which can leave a partial beta on crates.io and spends the token's 30 minutes on builds; committing the version inside the runner to get a clean tree, which would record a commit that exists nowhere else; asking the crates.io web API, which needs a User-Agent with contact details under its crawler policy.
