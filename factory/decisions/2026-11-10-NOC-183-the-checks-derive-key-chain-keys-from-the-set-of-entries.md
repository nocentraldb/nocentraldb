# 2026-11-10 · NOC-183 · The checks derive key chain keys from the set of entries, so every copy keeps the same key, and un-folding checks decryption again

- Decided by: coding agent (NOC-183)
- Why: RFC 0003 and RFC 0008 leave open, inside the core, which key chain entries a member opens and what wins when two give a key for one generation. `SealChecks` opens the previous keys only of entries the generation graph holds (valid when written), so a member that held a key without the admin role cannot plant keys. After every control change it drops its key chain keys and derives them again from the envelope keys to the member and the set of entries: in passes over the entries in change id order until a pass gives no new key, a generation keeps the first key a pass opens for it, and an envelope's key always wins. The keys so depend on the set of entries, never on their arrival order. No such rule can keep keys only growing (with only one of two disagreeing entries, a copy must keep that entry's key), so a key can be replaced; un-folding (RFC 0006) therefore checks step 5 again through `Checks::still_opens`, not only step 4, and `SealChecks` keeps the replaced keys, used only by `Checks::open_folded` to find what an un-folded change folded. Every copy then ends in the same states and the same fold.
- Instead of: keeping the first key the chain gave across arrivals (NOC-139), under which two copies that received two disagreeing entries from a misbehaving admin in different orders held different keys; opening every key chain entry that decrypts, which would let a writer that once held a generation's key hand members a wrong key for an older generation; or keeping a payload copy per folded change in the log to un-fold it, which would store content a second time.
