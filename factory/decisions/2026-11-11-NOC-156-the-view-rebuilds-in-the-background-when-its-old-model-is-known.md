# 2026-11-11 · NOC-156 · The view rebuilds in the background when the model of its old tables is known, and the SDK runs the pages in a thread of its own

- Decided by: the owner, NOC-227 A and A (2026-11-11), for the names `ViewReport`, `ViewStatus`, `RebuildProgress { folded, total }` and for the staging tables with the prefix `r_` and no marker; the coding agent (NOC-156, part B) for when a rebuild runs in the background and how the SDK drives it
- Why: RFC 0006 has the app read the old view while new changes fold into it, so the old tables must be served by the model they were folded by. The view keeps only that model's hash. When the hash is the stored lock's model, as after an app was rolled back to an older lock, `View::open_with` starts a rebuild and keeps serving by the old model. Otherwise it folds the whole log again inside the open, as before. `View::rebuild_step(frames)` folds the next frames of every space's log, in local-position order, into the staging tables, in a transaction of its own. At the end, the same transaction drops the old tables, renames the staging ones, creates the indexes, writes every change's rebuilt state and updates `meta`. Every open drops staging tables a cut-off rebuild left, so it starts again, as the owner chose. A page that fails rolls back and restarts the rebuild, since its in-memory logs had moved on. The SDK starts a thread named `nocentraldb-rebuild` when a rebuild runs. Under the database's lock it folds 128 frames at a time and notifies the followers. After the swap it reads and writes by the new model and touches every subscription. The view keeps the checks factory for the rebuild, so `open_with` asks for `Send + 'static` checks.
- Instead of: running the pages on the sync thread, which only a database with a relay has; holding the lock for the whole rebuild, which would block the app as before; a background rebuild when the old model is unknown, whose old tables could then not serve.
- What this does not do: a view folded by a model other than the stored lock's still rebuilds inside the open. One case: an app reopened with the newer lock after a rollback finished, whose tables the older lock folded. A rebuild that keeps failing stays reported until the next open. A rebuild does not yet run on wasm32, where the SDK starts no thread.
