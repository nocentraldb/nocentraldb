# 2026-11-15 · NOC-338 · Every message travels as base64 in one text frame, and no message is over 32 KB

- Decided by: Carsten, 2026-11-15, NOC-338 (option A, variant b: no message over 32 KB)
- Why: the first smoke test against the deployed relay dropped every connection. API Gateway's WebSocket APIs close a connection that sends a binary frame with code 1003 ("Binary media types for WebSocket APIs"), and the member sent every message as one. API Gateway's quotas also cap a frame at 32 KB and a message at 128 KB, closing with 1009 above either ("Amazon API Gateway quotas for configuring and running a WebSocket API"). Every message of RFC 0007 now travels as its standard base64 in one text frame, in both directions and to every relay, so there is one protocol. AWS does not document whether API Gateway joins a member's continuation frames into one message, as which frame type a `PostToConnection` reaches the member, or what a post above 32 KB becomes, and a browser cannot send one message as several frames; so no message is larger than one frame. The largest message is 23 KiB, 23,552 bytes, whose base64 is 31,404 characters, under 32 KB however AWS counts it, and a change whose frame does not fit, above 22 KiB, goes through an upload as larger changes already did. A member reads a message from a text frame, or from a binary frame holding the same base64, should API Gateway deliver a post as one.
- Instead of: option B, leaving API Gateway for a container behind a load balancer, a larger change to the AWS backend and its cost; base64 toward the AWS relay only, two encodings of one protocol; splitting a message above 32 KB into WebSocket continuation frames, which rests on behaviour AWS does not document and which a browser cannot produce; or chunks with a header of their own, which reach the Lambda function as separate invocations that would have to keep the parts of a message between them.
- Topics: relay, protocol, aws, browser
