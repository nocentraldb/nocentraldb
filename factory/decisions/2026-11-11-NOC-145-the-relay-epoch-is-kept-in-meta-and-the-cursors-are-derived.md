# 2026-11-11 · NOC-145 · The relay epoch is kept in the view's meta table, and each space's cursor is derived from the relay positions

- Decided by: coding agent (NOC-145), with pm; the `relay_epoch` key is an on-disk addition that waits for the owner's tick on the PR
- Why: a reopened database must know which relay epoch its relay positions belong to, or it has to forget them all (NOC-108's rule) and pull every space from 0. The view keeps the epoch under the key `relay_epoch` in its existing `meta` table, as 32 lowercase hex digits; the SDK writes it when `welcome` names a new epoch and reads it back on open. A space's cursor is not stored: `View::relay_cursor` derives it as the highest relay position up to which the log holds a change at every position. Derived this way it can be lower than the cursor the SDK held in memory, when a pulled entry never reached the log, but never higher, so a member that pulls from it re-reads at most a few entries and never skips one. A database without the key, kept before this change, behaves as before: its first `welcome` forgets every position without reporting `epoch_changed`. One whose stored epoch differs from the relay's now reports `epoch_changed`, because the epoch did change.
- Instead of: storing each cursor too, a second on-disk piece that can disagree with the positions and, if written ahead of the log, skip changes; a file of its own next to `nocentraldb.sqlite`, which the layout (NOC-144) leaves room for but which a copy of the database could separate from its log.
