# 2026-11-10 · NOC-86 · The core says what a merge rotation holds; the caller encrypts the previous keys

- Decided by: coding agent (NOC-86)
- Why: RFC 0008 (step 5 of "Two removals that rotate the key at once") has an admin write a merge rotation when the current generation is exposed: a key chain entry that lists every head as previous, with envelopes for the current members only. `Resolved::merge_rotation(admin)` returns it as `MergeRotation`: the generation id derived as "Generation ids" says, the heads, and the current members as recipients; it is none for a member that is not an admin, and when nothing is exposed. A merge rotation answers no revocation, so its key 10 is empty, as NOC-71's reading rules allow. Its entry takes each previous key as the caller encrypts it, because RFC 0003 fixes the key-chain subkey and the cipher but not the byte layout of an encrypted previous key (NOC-71); that layout is a wire format, which GENESIS.md reserves for the owner. When an admin writes the merge rotation, after a random delay (M15), is the SDK's. A current generation exposed with a single head, such as after a member left or a removal without a rotation, gets a merge rotation with one previous generation, which RFC 0008 lists under the same rule.
- Instead of: choosing a byte layout for the encrypted previous keys here, which would decide a wire format without the owner; or leaving the merge rotation entirely to the SDK, so that each SDK would derive heads, ids and recipients itself.
- Topics: rfc-0008, keys, membership, scope
