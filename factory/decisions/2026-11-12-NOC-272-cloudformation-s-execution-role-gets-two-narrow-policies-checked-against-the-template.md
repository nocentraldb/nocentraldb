# 2026-11-12 · NOC-272 · CloudFormation's execution role gets two narrow policies, checked against the template

- Decided by: coding agent (NOC-272), on pm's answer to PR 3's open points (NOC-264 point 4, least privilege)
- Why: CDK's bootstrap gives CloudFormation's execution role `AdministratorAccess` by default, which contradicts least privilege. The owner instead creates two managed policies from `infra/aws/execution-policy` (`storage.json`, `service.json`; one would exceed IAM's 6144 characters) and passes them to `cdk bootstrap --cloudformation-execution-policies` (docs/relay-deploy.md). Their actions are those CloudFormation's registry lists as the handlers' permissions for each resource type the stack uses (`infra/aws/test/cloudformation-handlers.json`, from the registry's schemas for eu-central-1), less a listed set the stack's configuration never reaches, each with its reason (Kinesis, customer managed keys, replicas, autoscaling, VPC, layers, log delivery, S3 Tables, replication, IAM users and groups). Each statement names the stack's own resources through `${aws:PrincipalAccount}` and the prefixes `NoCentralDbRelay-*` and `ncdb-*`, in eu-central-1; five read or metric actions with no resource-level support use `*`. The function's role may be passed only to Lambda, and only `AWSLambdaBasicExecutionRole` may be attached to it. `infra/aws/test/execution-policy.test.ts` synthesizes the stack and fails when a resource or parameter type is unknown, an action it needs is missing, the policies allow an action it does not need, a statement leaves the stack's resources or the region, or a resource gets a name of its own that the prefixes would miss.
- Instead of: keeping `AdministratorAccess`, which pm refused; one service-wide `*` per service, which would cover any resource of those services in the account; or a policy written from the CloudFormation docs by hand, with nothing to tell when the stack grows a resource type it does not cover.
