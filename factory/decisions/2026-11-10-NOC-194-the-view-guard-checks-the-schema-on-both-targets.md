# 2026-11-10 · NOC-194 · The SQLite option guard checks the view's schema and its page-size independence, on both targets

- Decided by: coding agent (NOC-194), following the owner's answer A on NOC-185
- Why: the owner decided that the native and browser SQLite builds share the release, not the compile options. The guard (`tests/view_sqlite_options.rs`) runs in the native tests and in the wasm32 test runner of `pnpm gates`, whose SQLite is the browser's build (sqlite-wasm-rs), so it needs no browser. It reads the view's schema after a fold and reports every virtual table (FTS, R-Tree or any other module) and every table with a foreign key (`pragma_foreign_key_list`), and it folds the same changes into databases of page size 1024, 4096, 8192 and 65536 and compares what the view holds. Fixtures of a foreign key, an FTS5 table and an R-Tree table show that the check fires, on both targets. A query that used FTS or R-Tree would need such a table, so checking the schema covers the queries; the plan check that `View::open` runs stays as it is.
- Instead of: a check of each build's `compile_options`, which would fail when a build gains an option the view does not use; or a test in the browser harness only, which `pnpm gates` does not run.
- What this does not do: it does not show that a build lacks FTS or R-Tree. A probe found that the gate's wasm32 build creates both, as the native build does; what differs between the builds in practice are the defaults, foreign keys on natively and off on wasm32, and a page size of 4096 natively and 8192 on wasm32. The guard keeps the view from relying on any of them.
