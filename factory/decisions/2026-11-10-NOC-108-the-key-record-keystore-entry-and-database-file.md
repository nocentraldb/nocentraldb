# 2026-11-10 · NOC-108 · The keys are one 113-byte record, kept in one keystore entry per database directory or in the key file

- Decided by: coding agent (NOC-108), pending the owner's answer on NOC-144, since GENESIS.md reserves on-disk formats and key handling for the owner
- Why: RFC 0003 and RFC 0009 (S19, S20) say where the member key and the account key live, not in which bytes or under which name. The record is the 16 ASCII bytes `nocentraldb-keys`, a format byte `1`, then the member signing secret, the member key-agreement secret and the account secret, 32 bytes each: fixed bytes that a `Zeroizing` buffer holds whole, the same in a key file and in a keystore entry, and no other format is read. The keystore entry has the service `nocentraldb` and, as its user, the canonical path of the database's directory. The SDK creates a key file it is asked for with `create_new`, mode 0600 on Unix. `path(dir)` holds one SQLite file, `nocentraldb.sqlite`.
- Instead of: a canonical CBOR map, which the SDK would copy through values that are not wiped; a database id kept in a file of its own as the keystore's user, which survives moving the directory but adds a second file the SDK must keep in step.
- What this does not do: moving or renaming the directory of a database whose keys are in the keystore loses the link to its entry, and opening it then fails with `StorageFailed` (see the next decision). A key file's permissions are not checked when it is read, and on Windows the file takes the directory's default access.
