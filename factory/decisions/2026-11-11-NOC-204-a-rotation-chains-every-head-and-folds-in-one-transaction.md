# 2026-11-11 · NOC-204 · A rotation chains every head and is folded with its call's other changes in one transaction

- Decided by: coding agent (NOC-204); the core's `View::receive_all` approved by pm (2026-11-11)
- Why: NOC-169's rotation listed only the current generation and folded each change in its own transaction, so a crash could leave an admin with a rotation it held no key of. The rotation's key chain entry now lists every head of the generation graph, as RFC 0008's merge rotation does ("Two removals that rotate the key at once", step 5), so the new generation descends from all of them and is the one head after it. An admin that does not hold the key of every head is refused with `InvalidValue` before anything is written, since it cannot seal a key it does not hold. A membership call writes all its changes first into a batch (`members/batch.rs`): the key chain entry, one envelope per member of the space in member-id order, the author included, then the add from the new generation after those envelopes, and the new member's envelope. The core folds the batch with `View::receive_all`, which receives every frame in one SQLite transaction: all of them, or, on any error or a crash, none. When the batch is refused, the space's checks, which learned its control changes in memory, are read again from the log. The rotation answers no revocation, and a space with a person key is still refused with `InvalidValue` (person-key re-wrap goes to its own tickets).
- Instead of: listing the current generation only, which left concurrent heads for a merge rotation to join later; skipping a head whose key the admin lacks, which would leave that generation a head; one SQLite transaction per change, which a crash could cut in the middle; a transaction the SDK opens around several `View::receive` calls, which the view's API does not offer and would let the SDK see the connection.
- What this does not do: it does not re-wrap person-key records, and it writes a merge rotation only as part of a membership call, not on its own when the current generation is exposed (RFC 0008, step 5).
