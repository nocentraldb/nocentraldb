# 2026-11-10 · NOC-71 · The generation graph where RFC 0008 leaves a detail open

- Decided by: coding agent (NOC-71)
- Why: RFC 0008 ("Generation ids", "The function", "Two removals that rotate the key at once") defines the graph but not each detail, and each must depend only on the set. (1) The graph of a set holds the first generation and the generation of every key chain entry in it that is valid when written, whatever its final verdict (M17); `resolve` builds it for every causal past as well as for the whole set, so "a generation exists" in step 1 reads the graph of the change's causal past. (2) Each generation keeps the key chain entries that name it with their authors, and the recipient of every key envelope for it in the set, whatever the envelope's verdict, because a rejected envelope may still have been delivered; envelopes for a generation the graph does not hold are not recorded. (3) Two accepted key chain entries that name one generation id are both rejected as `DuplicateGeneration` (M23), a new rejection; the generation stays in the graph, since both entries were valid when written. Honest authors cannot produce this, but an admin that rotates twice from the same view can. (4) "Descends from" includes the generation itself, and a generation not in the graph descends from nothing. (5) The state's canonical encoding carries the graph, so the convergence harness compares it. (6) This narrows item 3 of `2026-11-09-NOC-67-resolve-details-rfc-0008-leaves-open.md`: key envelopes and key chain entries now meet their own rules in step 1; entry types 4 to 6 are still judged on the right alone.
- Instead of: dropping a generation whose key chain entry a later revocation rejects, which RFC 0008 rejects (M17); or keeping one of two entries with the same id, which RFC 0008's M23 rejects.
- Topics: rfc-0008, membership, convergence, keys
