# 2026-11-12 · NOC-176 · nocentraldb exposes its bridge behind a hidden feature

- Decided by: Carsten, 2026-11-13, on #290; proposed by the coding agent, recommended as A by pm
- Why: NOC-274 point 1 puts the wasm export in the crate `nocentraldb-wasm` so that `nocentraldb` keeps its browser calls crate-internal. The bridge, which answers the worker's CBOR requests, needs internals of `nocentraldb` (`OpenOptions::browser`, `Value`'s representation, an object's fields, `Transaction::create_at`), so it lives in `nocentraldb`, and `nocentraldb-wasm` can reach it only through something `nocentraldb` exports. `nocentraldb` gains the cargo feature `bridge`, off by default, under which one `#[doc(hidden)] pub mod bridge` holds `Bridge::new()` and `Bridge::handle(&mut self, &[u8]) -> Vec<u8>`: CBOR bytes in, CBOR bytes out. Only `nocentraldb-wasm` turns the feature on. No browser call of the Rust SDK becomes a public Rust name; the message protocol is the only surface, and the TypeScript SDK mirrors it. The protocol is not versioned, because `@nocentraldb/sdk` ships the worker, the wasm module and the TypeScript that speaks to them in one build.
- Instead of: the module always `#[doc(hidden)] pub`, without a feature (B), which every user of the Rust SDK would compile; the dispatch in `nocentraldb-wasm` with the internals it needs made public (C), which NOC-274's decision rules out ("a `nocentraldb::wasm` module, which would make `OpenOptions::browser` a public Rust name").
- Topics: sdk-ts, sdk-rust, browser, wasm, api
