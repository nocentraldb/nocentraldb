# 2026-11-11 · NOC-180 · An invitation's layout holds only what a reader cannot rebuild, and reading it checks the shape alone

- Decided by: coding agent (NOC-180), carrying out the owner's NOC-141 A (Carsten, 2026-11-10): `ncdb-invite-1:` plus unpadded base64url of a fixed binary layout that starts with a version byte, holding only public data
- Why: the layout leaves out the member id, certificate key 4 and the statement's account key, because a reader rebuilds them: the member id from the two public keys (RFC 0003, "The member key"), key 4 because a database's member is never a sub-agent, and the statement's account key because it must equal the certificate's. A field that is not stored cannot disagree with the one it would repeat, so the reader needs no check for that. The one optional part, the account key statement, has a presence byte, so a layout is 163 or 267 bytes. `FromStr` refuses every text whose shape is wrong with `InvalidValue`, but does not verify the signatures: `members().add` already checks the certificate and refuses it with `invalidCertificate`, and one check in one place keeps the two from drifting. `Display` and `FromStr` were taken over a function of its own because RFC 0009 names them for Rust.
- Instead of: storing the member id and checking it against the keys; verifying the certificate while parsing; a length field in place of the presence byte.
- What this does not do: it does not give a sub-agent an invitation, and it does not give `MemberId` or `Fingerprint` a text form.
- Topics: sdk-rust, rfc-0003, members, invitation
