# 2026-11-12 · NOC-272 · The relay deploys from main through OIDC, and builds its package in the deploy job itself

- Decided by: coding agent (NOC-272), following NOC-264 (point 4 B, as the owner confirmed it) and pm's answers on the plan
- Why: `relay-deploy.yml` has two jobs. `build` runs on pull requests and on pushes to `main` that touch the relay, with no AWS access: it installs cargo-lambda and zig pinned by version and wheel hash (`infra/aws/cargo-lambda.txt`) and builds the function's arm64 package. `deploy` runs only on a push to `main`, in the environment `aws-prod`, which allows only `main`. It is the only job with `id-token: write`. It assumes `AWS_DEPLOY_ROLE_ARN` through OIDC with `configure-aws-credentials` pinned by SHA, builds the package again in its own job, so it deploys exactly what it built, shows `cdk diff`, then runs `cdk deploy`. The deployment's values come from the environment's variables and reach the shell as variables. The deploy role, set up once by the owner (docs/relay-deploy.md), trusts only `repo:nocentraldb/nocentraldb:environment:aws-prod` and may only assume CDK's bootstrap roles. A pull request's infrastructure diff is the committed template snapshot (pm, answer C), and there is no second, read-only role. `scripts/relay-deploy-workflow.test.mjs` holds this contract, each check with its mutants.
- Instead of: handing the package from the build job to the deploy job as an artifact, which adds an action and a hand-over a deploy would have to trust; a manual deploy from the owner's machine, which NOC-264 replaced with point 4 B; or `workflow_dispatch`, which would let a run start outside a merge to `main`.
- Topics: relay, aws, deploy, ci, oidc
