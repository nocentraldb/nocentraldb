# 2026-11-11 · NOC-175 · The SDK builds for wasm32 in memory first, refuses a relay there, and reads the wall clock through `src/clock.rs`

- Decided by: coding agent (NOC-175, slice 1); the gates' wasm tests and the dependencies are the owner's (Carsten, 2026-11-11, NOC-210 A, A, A)
- Why: the first slice of the SDK in the browser makes it build and run on wasm32-unknown-unknown in memory, so the later slices (the database on OPFS, keys in IndexedDB, syncing over the browser's WebSocket) each add one thing to a crate that already builds there. tokio keeps only its `sync` feature on wasm32, for the channels a database holds on every target; the runtime, sockets and timers, the WebSocket client and `ncdb-relay` are native only, and so are `sync::run` and `sync::session`, the code that holds a connection. A database opened with a relay on wasm32 is refused with `InvalidValue` ("syncing with a relay is not built on wasm32 yet") rather than opened without syncing, which an app could not tell from a relay that is down. The wall clock is read in one place, `src/clock.rs`: `SystemTime` natively, and JavaScript's `Date.now()` through `js-sys` on wasm32, where `SystemTime::now` panics; no `web-time` crate (NOC-210 Q2 A). `getrandom` takes its `wasm_js` backend on wasm32, as the core's does. The SDK's gates build it for wasm32 (`build-wasm`) and run its in-memory tests there under wasm-bindgen-test in Node (`test-wasm`), as the core's do (NOC-210 Q3 A); the sync, relay, keystore and reopen tests stay native, since they need sockets, threads, a file system or a keystore.
- Instead of: a database that opens with a relay on wasm32 and never syncs, which reports `Connecting` forever; `web-time` for the clock, a dependency the owner did not take; a second, wasm-only copy of the SDK's in-memory tests.
- What this does not do: the database at a path, keys in IndexedDB and syncing in the browser are later slices of NOC-175; until then a database at a path on wasm32 fails where the platform has no file system or keystore.
