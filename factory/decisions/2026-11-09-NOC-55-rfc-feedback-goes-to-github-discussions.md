# 2026-11-09 · NOC-55 · RFC feedback goes to GitHub Discussions, one discussion per RFC that holds a pointer

- Decided by: owner (Carsten, 2026-11-09), by merging #65, the proposal of NOC-53
- Why: feedback on an RFC lives in GitHub Discussions, in the category "RFC feedback": each RFC gets one discussion named after it, people reply there one topic per reply, a point that needs room of its own gets a new discussion through the form, and a change to the text is a pull request against the RFC's file. Every reply has a URL that an amendment can link, and the discussion outlives the RFC's pull request. An RFC's discussion holds a short pointer to the file (a summary, the link and the questions where we want advice), not a copy, because a copy drifts with every amendment, as #21's copy of RFC 0001 already did. Announcing outside the repository waits until three things are true: the repository is public, the RFC's discussion is current, and someone can answer within a week, as `docs/rfc/README.md` promises; the owner decides each announcement and posts it. pm reads the category over REST on every tick and drafts answers; the owner reviews and posts them (`factory/roles/pm.md`).
- Instead of: GitHub issues per RFC or per point, which read as work and mix with bug triage; comments on the RFC's pull request, which stop when it merges; or an outside channel as the home, which we do not own and cannot link back to reliably.
