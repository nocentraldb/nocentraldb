# 2026-11-13 · NOC-281 · Alphas reach npm from a job of their own, alpha-npm, which holds only id-token: write and contents: read

- Decided by: Carsten, on the NOC-281 PR (pending tick)
- Why: the owner decided on NOC-274 (point 7) that alphas of the TypeScript SDK go to npm under the dist-tag `alpha`, through Trusted Publishing and with provenance. The publish needs the job's OIDC token (`id-token: write`); the GitHub prerelease needs `contents: write`. A job of its own, `alpha-npm`, after the alpha job, keeps the two apart: no step that builds and runs the package's code holds a write token to the repository, and the job that tags holds no token npm would accept. It runs `scripts/release/npm-publish.mjs`, which publishes what `publishable.mjs` lets through, refuses a package that is not at the alpha's version or whose `repository.url` does not name the repository (npm checks provenance against it), and skips a version npm already holds, so "Re-run failed jobs" publishes only what is missing. The owner publishes the placeholder `@nocentraldb/sdk@0.0.0` once by hand and configures the trusted publisher for `release.yml` (docs/release-management.md, "Publishing @nocentraldb/sdk for the first time").
- Instead of: the npm step inside the alpha job, which would give `id-token: write` to a job that holds `contents: write` and runs the build; an npm token in a repository secret, which GENESIS's supply-chain rules and docs/release-management.md rule out; and publishing from the `build` side's artifact, which serves betas and releases on tags, not alphas.
- Topics: release, npm, supply-chain, sdk-ts
