# 2026-11-20 · NOC-373 · An install line names a version only once its registry serves it, and is the previous line until then

- Decided by: coding agent (NOC-373), for the owner's review on the PR
- Why: `commit-back` indexes a beta or release in `release-notes/index.json` as soon as npm has it staged, but npm serves it only after the owner approves it (NOC-346, NOC-374). When the site is built, it asks npm whether the newest indexed version is under its dist-tag (`beta`, or `latest` for a release) and crates.io whether it serves that version unyanked. Each line follows its own registry: the npm line names the newest indexed version once npm serves it, the cargo line once crates.io does, so for a while the two may show different stages. Until then a line is the previous one: the line of the version indexed before it, or the alpha line before the first beta. The site does not ask the registry about that previous version: it was indexed before, so it was published, and a registry that cannot be reached leaves the same previous line, without failing the build. A crate with `publish = false` keeps coming from the newest indexed tag in git, since a git tag needs no registry. The answer is kept for an hour in `site/node_modules/.cache/ncdb-registry.json`, so every page of one build and the output check after it show the same lines. The site rebuilds once a day, because no push follows the owner's approval on npm.
- Instead of: showing the indexed version at once, which tells visitors to install a beta npm cannot install yet; walking back through every indexed version and asking the registry about each; a cargo line from git at the newest tag while crates.io lags, which the ticket's "previous working line" does not describe; failing the build when a registry is down; and a step in the release workflow after the approval, which cannot exist, since only a person approves on npm.
- Topics: site, release, npm, crates-io
