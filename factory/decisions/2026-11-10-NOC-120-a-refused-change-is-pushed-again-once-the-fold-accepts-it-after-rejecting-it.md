# 2026-11-10 · NOC-120 · A refused change is pushed again once the fold accepts it after rejecting it, by clearing its refusal

- Decided by: coding agent (NOC-120), the core method and the behaviour on pm's answer to Q5
- Why: M19 says a member pushes a refused change again "whenever its own fold newly accepts the change after a control change arrived". The SDK reads "newly accepts" as a move from rejected to folded after the relay's refusal. A change that was folded when refused and stays folded is not pushed again. Each refused change is kept in the sync state, in memory, with whether the fold has rejected it since. The SDK checks after every change it pulls, and before every push, so that a control change the member wrote itself counts too. A database that opens takes the refused changes from its log with their current state, so a rejection seen before a reopen still counts after it. When a rejected one is folded again, ncdb-core's new `View::clear_refusal` sets its `relay_refusal` to NULL and updates the log's relay counts. The change is then unconfirmed and `View::unconfirmed` pushes it once more. If the relay accepts it, it no longer counts as refused. If the relay refuses it again, the refusal is recorded again and only another move from rejected to folded pushes it, so nothing loops. The on-disk format does not change.
- Instead of: a queue in memory of changes to push again, which a reopen would lose and which would leave the change counted as refused after the relay accepted it; or pushing every refused change again after every control change, which M19 does not ask and which could repeat a push that the relay would refuse again.
- What this does not do: the relay's earlier code for the change is gone once the refusal is cleared. A change rejected and folded again within one change that the member received is caught, because the SDK checks after each one. A rejection and a re-acceptance that both happen while the database is closed are not seen as a move from rejected to folded.
