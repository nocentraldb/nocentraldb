# 2026-11-10 · NOC-158 · The relay's `not_member` or `removed_member` marks the member removed from the space, and `SyncStatus::error` reports it

- Decided by: coding agent (NOC-158), the safe subset
- Why: the relay serves no change to a member that is no longer current, so the member's copy never folds its own removal, and `spaces().list()` kept the last role it folded (NOC-151). RFC 0007 says on `not_member` and `removed_member` "stop syncing the space; the SDK reports it", and RFC 0009 gives a removed member the role `"removed"` while it keeps reading its copy. So once the relay answers either code for a space, the SDK stops syncing it, `list()` shows it with `role: None`, a write into it and `members().add` fail with `NotMember` before anything is written, and `spaces().get` and every read still serve the copy. RFC 0009 reports the role per space in `space.status`, which is not built (NOC-120); until it is, `SyncStatus::error` carries the code, as the last error that stops syncing, and keeps it after a reconnect while no error of the connection, such as `unsupported_version`, replaces it. Which spaces were stopped, and the stop itself, are kept in memory: a reopened database syncs the space again, and the relay answers `not_member` again.
- Instead of: a new field of `SyncStatus` for the stopped spaces, a public name the owner has not seen; or clearing the code at the next `welcome`, which would hide a removal the member's copy cannot fold.
- What this does not do: `SyncStatus::error` names the code but not the space; an app finds the space in `spaces().list()`. A write in a space whose folded membership no longer gives the member a role, without the relay's answer, is NOC-136.
