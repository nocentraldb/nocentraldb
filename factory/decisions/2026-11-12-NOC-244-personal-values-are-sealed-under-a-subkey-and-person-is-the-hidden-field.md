# 2026-11-12 · NOC-244 · Personal values are sealed under a person-key subkey, and $person names a person's key

- Decided by: Carsten, 2026-11-12, on NOC-244 (A to all twelve questions)
- Why: a personal value is sealed with XChaCha20-Poly1305 under HKDF-SHA256(person key, "nocentraldb/personal-value"), with the associated data "nocentraldb/personal-value" || space id || object id || person-key id || collection and field name, each with a 2-byte length, laid out nonce || ciphertext || tag, its plaintext the canonical CBOR of the value; it sits as argument 1 of a set, `replaces` readable, and a clear is a plain null; the hidden field `$person` on the person's object names the person id and the person-key id; an erased field reads as unset and is named in `$erased` (`object.erased()`); a value whose key is not held yet reads as unset; `ErrorCode::NoPerson`, `tx.create_with(..., Create { same_person_as })`; values sealed under a losing first person key read as unset in v1; the erasure call stays with the work-order RFC.
- Instead of: a CBOR map as associated data, the person key used directly, the nonce as a key of its own, a type-tagged plaintext, the sealed value directly in key 5, a sealed null, a person-key id derived from the person id, the person id only on sealed values, an error on reading an erased field, a status of fields whose key is missing, a builder for create's options, and re-sealing values under the chosen key.
- Topics: personal-fields, crypto, rfc-0002, rfc-0003, rfc-0004, rfc-0005, rfc-0009, api
