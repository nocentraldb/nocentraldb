# 2026-11-10 · NOC-164 · The relay server holds at most 512 connections, 64 of them in the handshake, and drops one above either limit at accept

- Decided by: coding agent (NOC-164), within RFC 0007's "Liveness"
- Why: without a limit, peers that open connections fast each hold a task, a file descriptor and an outgoing queue until their handshake deadline passes, or for good once they authenticate. Each connection now takes a place among `MAX_CONNECTIONS` (512) for as long as it is open, and one among `MAX_HANDSHAKES` (64) until it is sent `welcome`; tests set both with `Server::with_max_connections` and `Server::with_max_handshakes`. A connection without a place is dropped right after `accept`, before the WebSocket upgrade, without an error message: "Liveness" lets a relay close any connection at any time, and the member reconnects with back-off. No RFC 0007 code fits: `rate_limited` is a member's or a space's quota, which is unknown before `auth`, and `unavailable` is a backend failure; and sending either would need the upgrade, which costs the very task and time the limit saves. 512 stays below the 1,024 file descriptors many systems give a process by default, and bounds all outgoing queues together at 2 GiB (512 × 32 messages × 128 KiB). 64 handshakes are far more than members on a working network need at once, since each finishes its handshake in well under a second.
- Instead of: a public `ncdb-relay` command-line option for either limit, whose name is the owner's (NOC-164 asks pm first); sending `rate_limited` or `unavailable`, or an HTTP 503 to the upgrade, which each need the peer's request read first; a per-address limit, which a proxy on the loopback would defeat, since every connection then comes from 127.0.0.1; or waiting for a free place before `accept`, which leaves new peers in the kernel's backlog with no answer.
- What this does not do: peers that fill the 64 handshake places keep new members from connecting, each for up to 30 seconds (three steps of 10), while members already connected stay unaffected; the limit protects the server's resources, not its availability to new members. It does not tell the member why it was closed; the member sees a failed connection and backs off. Members past 512 cannot connect, and raising the limit needs a release until it becomes an option.
