# 2026-11-20 · NOC-389 · A member reads a generation with the key its control change confirms

- Decided by: Carsten, 2026-11-20 (option A on NOC-389: keep every key the envelopes of a generation unwrap to); the rule below it for the owner's review in the PR
- Why: a member kept one key per generation, the last envelope's, so a wrong-key envelope that arrived last made it reject sealed changes it could read. Its own verdict depended on arrival order (principle 2), and a member who can write an envelope could blind another member to a generation. The core now keeps every key the envelopes to it unwrap to. When it holds several for a generation, the generation's key is the one under which the generation's own control change opens: the genesis's sealed `model.id` for the first generation, the key chain entry for a later one. The member opens and seals every change with that key alone. Until that change arrives, the generation has no key on that member, and its changes wait as "no key". A lone key is used as before. `SealChecks::wrong_envelopes` lists each envelope the control change does not open under, with its author, as a local report; the SDK does not show it yet. Nothing on the wire or on disk changes, and RFC 0003's rule that a member opens a ciphertext with one key holds for every sealed change.
- Instead of: trying every held key on each sealed change and folding it when exactly one opens it, which let a member fold a change sealed under a wrong key that members with only the right key reject; keeping only the first envelope per generation in change id order (option B), which is order-independent, but a wrong envelope with a lower id would still blind the member.
- Topics: crypto, keys, membership, convergence
