# 2026-11-19 · NOC-374 · Betas and releases reach crates.io and npm from two jobs of their own, after the GitHub release, and commit-back waits for both

- Decided by: coding agent (NOC-374), for the owner's review on the PR
- Why: the ticket asks for a crates.io job that holds only `id-token: write` and `contents: read`, as `alpha-npm` does (NOC-281). The `publish` job holds `contents: write` for the GitHub release, so neither registry can publish from it. `publish-crates` and `publish-npm` each hold only the OIDC token and read, check out the tagged commit without keeping a token, write the version with `set-version`, and send through `crates-publish.mjs` and `npm-publish.mjs`. Two jobs instead of one: a failure in one registry does not hold the other back, "Re-run failed jobs" re-runs only the one that failed, and the npm build's toolchain (wasm-bindgen, the SDK build) stays out of the crates job. Both wait for `publish`, so the GitHub release exists before a registry holds the version, as for alphas. `commit-back` waits for both, so `release-notes/index.json` lists a version only once crates.io holds its crates and npm its staged packages. `npm-publish.mjs` serves betas and releases too: the dist-tag must match the version's stage (alpha, beta, latest), and a beta or release is staged with `npm stage publish`, as NOC-346 decided.
- Instead of: one job for both registries, where an npm failure forces a crates re-run and the job builds both toolchains; registry steps in `publish`, which would give the OIDC token to a job holding `contents: write`; and letting `commit-back` run before the registries, which would index a version a registry may never get.
