# 2026-11-27 · NOC-553 · A rich-text field declares its vocabulary in the schema and the lock, which may only grow, and the binding refuses an editor that differs from it

- Decided by: Carsten, 2026-11-27, NOC-553
- Why: the editor's extensions decide what a rich-text field stores, and adding one silently widened what the same field may hold with nothing in the data model recording it. Declaring the nodes and marks in the schema and the lock (`nc.richText({ vocabulary: { nodes, marks } })`) makes that change visible in the lock and versioned with the model. `ncdb model build` and the check on the device accept added names and refuse a removed one, a narrow exception to RFC 0011's rule that a field's configuration never changes: an added name takes nothing from an older client, whose binding keeps editing through its three measures, while a removed name would orphan content a newer client wrote. The binding reads the vocabulary from the lock and refuses at start an editor that differs from it in either direction, so a drift between editor and model is an error at development time; a document with undeclared names is reported as not fully shown, with that reason. The vocabulary is no part of the merge rule, so the core's fold and its Markdown rendering (NOC-440) stay as they are, and an older core that ignores the key folds the field the same way.
- Instead of: keeping the lock without a vocabulary, with the app keeping one module of its editor's extensions that the editor and the binding both import, which records nothing in the data model; the core enforcing the vocabulary by refusing updates with undeclared names, which would stop an older client from folding a document a newer client extended and fold the same changes differently on different app versions.
