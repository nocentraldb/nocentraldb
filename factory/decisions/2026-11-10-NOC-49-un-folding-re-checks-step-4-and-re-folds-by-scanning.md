# 2026-11-10 · NOC-49 · Un-folding re-checks step 4 of folded sealed changes and folds what they touched again by a scan

- Decided by: coding agent (NOC-49)
- Why: RFC 0006 ("Un-folding") says a sealed change that a later control change makes fail moves to rejected and the fold refolds every field it touched from the changes still folded, and allows, not requires, a bookkeeping table for the lookup. (1) After D11's re-check of rejected changes reaches its fixpoint, the log asks `Checks::is_member` again for every folded sealed change; a change that now fails moves to rejected as "not a member". Only step 4 is asked: the authors' keys and the space keys only grow as control changes arrive (NOC-78), so a change that passed steps 3 and 5 keeps passing them, and `Checks` now states that as a requirement. (2) `Fold` gains `clear_field` and `clear_object`; the log clears every field and object the un-folded changes folded into, then opens the changes still folded again and folds their operations on those targets, in log order. A field's state is a function of its set of operations, so the order does not count. (3) `SqlFold` clears the field's state and column, takes an object out of the deleted state, and removes a row of `c_<collection>` that neither a field state nor a create into the collection holds, so the tables equal those of a view that never folded the change. (4) `View::receive` writes the state of every change whose state the log set while receiving, instead of only the changes that were rejected before.
- Instead of: a bookkeeping table from object and field to operations, which is a second copy of the log that could disagree with it and is an optimisation the RFC leaves open; re-running every step on folded changes, which would decrypt and fold them again; or an undo per field type, which RFC 0004's merge states do not support.
- Topics: rfc-0006, rfc-0008, log, convergence, view
