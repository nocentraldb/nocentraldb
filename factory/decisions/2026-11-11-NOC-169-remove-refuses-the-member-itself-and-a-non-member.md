# 2026-11-11 · NOC-169 · `members().remove` refuses the member itself and a non-member, and takes its cutoff from the log

- Decided by: coding agent (NOC-169)
- Why: RFC 0008 lets any member remove itself (leave), but "a member that leaves cannot rotate, because it must not know the next key", while `remove` always rotates (RFC 0003's eager rotation). So `remove` of the database's own member is refused with `InvalidValue`, before anything is written, and leaving stays `space.leave()`, which is not built. A `MemberId` that is not a current member of the space, because it never was or was removed already, is refused with `NotFound`, a code RFC 0009 has, instead of writing a removal the fold would take as a no-op. The cutoff is the subject's highest author sequence the admin's log holds (`Tips::next_sequence - 1`, 0 when it holds none), as RFC 0008's "The cutoff" defines it. The rotation answers the removal, chains every head, and its envelopes go to every remaining member and never to the removed one; the removal, the key chain entry and the envelopes are one batch, folded in one transaction (NOC-204).
- Instead of: a removal of itself without a rotation, which would make `remove` behave two ways and is what `leave` is for; a new error code for a member that is not a member, which RFC 0009 does not name.
- What this does not do: it does not warn an admin who removes a member whose recent changes it has not received yet (RFC 0008, "A member removed while offline who keeps writing"); those changes, above the cutoff, are rejected everywhere.
