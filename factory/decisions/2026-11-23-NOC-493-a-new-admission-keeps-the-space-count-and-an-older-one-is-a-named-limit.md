# 2026-11-23 · NOC-493 · A new admission keeps the space count; re-presenting an older one is a named limit; the SDK names of admission

- Decided by: Carsten, 2026-11-23, on NOC-493 ("Ich stimme den Empfehlungen zu.")
- Why: RFC 0015 says a later admission replaces the earlier one, so the app "renews an admission, or raises its spaces, by issuing a new one". (1) The relay therefore replaces `until`, `spaces` and the admission key, and keeps the count of spaces created: renewing alone grants no fresh allotment, which an app renewing monthly would otherwise give every user without meaning to. (2) An admission carries no issue time, so a member can present an older admission that has not lapsed. This is built as written and named under "What it does not do" in RFC 0007; an app bounds it by choosing a short `until`, which the SDK renews through the same function. (3) The public names: TypeScript `db.account.identity: string | null`, null while the database waits to be paired; Rust `db.account().identity() -> Option<String>` and `OpenOptions::admission(f)`, where `f` takes the identity and returns a future of the admission text. If the app's function fails or returns a text that is not `ncdb-admit-1:`, the genesis stays refused with `not_allowed` and the sync status reports it.
- Instead of: resetting the count with each admission; an issue time in the token format that lets the relay refuse an older admission; never lowering `spaces` or `until`; other names.
- Topics: relay, admission, sdk-api
