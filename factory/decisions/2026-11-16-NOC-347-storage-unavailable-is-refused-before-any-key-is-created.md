# 2026-11-16 · NOC-347 · `storageUnavailable` is refused in the SDK's browser open path, before any key is created; ncdb-core is unchanged

- Decided by: coding agent (NOC-347); the code's name, `storageUnavailable` (Rust `ErrorCode::StorageUnavailable`), is proposed to the owner in the PR for confirmation
- Why: the core's `view::browser::install` still reports `Storage::Memory` when OPFS is missing, and `nocentraldb`'s `browser::place` turns that into the error right after the install, before `exists`, `reserve` and `load_or_create`. So a refused open writes no key record into IndexedDB and leaves nothing behind. The name pairs with `keyStoreUnavailable`, the other open error for storage the platform does not offer, and it names the cause the SDK detects (no OPFS), not "private window", since the SDK cannot see the window's kind and Chromium's private window opens. In the browser's open path, the in-memory branch to `Storage::Temporary` is removed; `Storage::Temporary` stays for a database opened `in_memory()` natively and with Node.js's `inMemory`.
- Instead of: changing `install()` in ncdb-core to fail where OPFS is missing, which would also take the in-memory VFS from the core's own wasm32 tests and needs the owner's review of the core; reusing `storageFailed`, which an app cannot tell from a damaged database; the name `privateWindow`, which claims more than the SDK detects.
- Topics: browser, sdk-ts, sdk-rust, errors, private-window
