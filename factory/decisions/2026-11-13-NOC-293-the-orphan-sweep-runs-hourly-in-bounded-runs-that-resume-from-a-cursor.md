# 2026-11-13 · NOC-293 · The orphan sweep runs hourly in bounded runs that resume from a cursor

- Decided by: pm, on NOC-293 (option A); the cursor's place is the owner's open question NOC-306
- Why: NOC-290's sweep ran once a day as one pass over `frames/` inside the function's 29-second timeout. Once the bucket outgrows one run, every run would start again from the beginning and never finish. Now each run gets a budget: Lambda's deadline for the invocation, less 5 seconds (`SWEEP_MARGIN`). When the budget is spent, the run stores the last key it visited and logs its end as `"pass":"paused"`; the next run lists `frames/` after that key. A run that reaches the end of the listing logs `"pass":"completed"` and stores when the pass completed, and no new pass starts within 23 hours of it (`PASS_EVERY`), so the rule runs every hour and a pass starts about once a day. The cursor is a reserved item in `spaces`, the 5 bytes `sweep`, beside the epoch item. `load` and `save` in `ncdb-relay-aws/src/sweep.rs` are the only code that knows that, so a table of its own (NOC-306 B) is a change to those two functions. A third alarm, `SweepPassOverdue`, mails the owner when no pass completed in two days; `SweepUnfinished` still catches a run that was cut off or crashed. The emulator test sweeps a bucket of 8 objects at 3 a run and checks that the pass completes in 3 runs, that the frames of changes are kept, and that a second pass waits a day.
- Instead of: a sweep function of its own with a longer timeout (NOC-293 B), which adds a resource; raising the shared function's timeout (C), which lets a stuck WebSocket invocation run past API Gateway's 29-second cap; or keeping the cursor in the schedule's input, which is fixed for every run.
