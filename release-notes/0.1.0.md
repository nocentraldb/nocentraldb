# 0.1.0

NoCentralDB 0.1 is the first release of a database that keeps a full copy of its data on each member's device and encrypts every change on that device before it syncs, through a relay that cannot read it. It ships the Rust SDK `nocentraldb`, the TypeScript SDK `@nocentraldb/sdk` for the browser, the CLI `ncdb` that builds a model's lock, and a relay that runs locally on SQLite or serverless on AWS. With it, an app shares spaces between people, devices and agents, keeps a person's devices in one account that survives a lost device, and erases a person's personal data from every member.

## Breaking changes

0.1.0 is the first release, so no code written against a release breaks. The changes below break code written against the 0.1.0 alphas.

### The TypeScript SDK refuses to open in a browser without OPFS

<!-- private-window-refuses-to-open · tickets: NOC-347 -->

In a private window of Safari or Firefox, which has no OPFS, the SDK kept the database in the memory of one tab. When that tab closed, or another tab took the database over, the changes the relay had not confirmed were lost, and `db.durability` reported none unconfirmed. `nc.open` now fails there with the new error code `storageUnavailable`, before it stores a key; `docs/browser-durability.md` has a text to show the user. Chromium's private window has OPFS and still opens.

**Migration.** Replace a check for `storage: "temporary"` with a catch of `storageUnavailable`. A browser no longer reports `"temporary"`.

```ts
try {
  const db = await nc.open({ model, lock, name: "tasks" });
} catch (error) {
  if (error instanceof nc.Error && error.code === "storageUnavailable") {
    showPrivateWindowNotice();
  } else throw error;
}
```

### A deprecated collection leaves the model's TypeScript type

<!-- typed-schema-and-collection-deprecation-api · tickets: NOC-80 -->

The schema functions now carry what each field reads as, which `nc.Infer` needs, and a collection can be deprecated (see "Models, the lock and `ncdb model build`" below).

**Migration.**

- TypeScript: code that names `model.<collection>` of a collection it has deprecated no longer compiles; remove that use, which the deprecation intends. `nc.set(...)` no longer takes a deprecated field as its element, which `ncdb model build` already refused. Code that only declares schemas needs no change.
- Rust (`ncdb-core`): `model_lock::Collection::deprecated` is an `Option<Deprecation>`, like a field's. Read the version as `collection.deprecated.as_ref().map(|d| d.since)` and the reason as `d.reason`. Construct `Collection` and `DraftCollection` with the new values; `deprecated: None` keeps the old meaning.

### Schema and index types changed in the TypeScript API report

<!-- nc-ref-in-the-schema · tickets: NOC-99 -->
<!-- sdk-ts-queries-and-subscriptions · tickets: NOC-176 -->

`nc.ref` and typed index queries reworked the types the schema functions return. The internal types every field shares (`Field`, `Fields`, and the condition `nc.Infer` uses to leave out deprecated fields) changed so that a field without `.personal` fits in a collection, and `nc.collection(fields, { indexes })` and `nc.index(fields, { equal })` now return types that carry the indexes and the equality prefix.

**Migration.** Calls compile unchanged, and every schema that compiled before builds the same lock. Only code that names these types or the old return types explicitly changes.

### `MemberInfo` in Rust is `#[non_exhaustive]`

<!-- sdk-rust-member-linked-to · tickets: NOC-269, NOC-307 -->

`MemberInfo` gained the field `linked_to` (see "Spaces and members" below).

**Migration.** Read its fields as before. An app can no longer build a `MemberInfo` with a struct literal, and a `match` on it needs `..`.

### An erasure's `state` gains `"waiting"`

<!-- erasures-list-a-waiting-shred · tickets: NOC-401 -->

The erasure audit now lists an erasure that waits for changes it depends on (see "Auditing an erasure" below).

**Migration.** In TypeScript, a `switch` on an erasure's `state` that checks it is exhaustive needs a case for `"waiting"`. In Rust, `ErasureState` is `#[non_exhaustive]`, so a `match` on it already has a wildcard arm.

### Code that uses `ncdb-core` directly

<!-- change-id-in-ids · tickets: NOC-248 -->
<!-- checks-learn-from-control-changes · tickets: NOC-78 -->
<!-- core-verdict-waiting · tickets: NOC-391 -->
<!-- current-generation-exposure-and-merge-rotations · tickets: NOC-86 -->
<!-- fold-creates-and-deletes-objects · tickets: NOC-39 -->
<!-- member-log-real-checks · tickets: NOC-48 -->
<!-- re-grants-and-the-generation-graph · tickets: NOC-71 -->
<!-- sqlite-local-view · tickets: NOC-69, NOC-77, NOC-81 -->
<!-- un-fold-after-a-late-revocation · tickets: NOC-49 -->

`ncdb-core` is the building block under both SDKs. An app that uses only an SDK needs none of these changes. Code that implements the core's traits or matches its enums does:

- **Ids.** The change id, operation id, member id and clock value moved to the new crate `ncdb-plugin`, since a plugin field type sees them; `ncdb_core::ids`, `ncdb_core::clock`, `ncdb_core::field::Outcome`, `ncdb_core::field_op::Origin` and `ncdb_core::cbor` keep their paths as re-exports. `ChangeId::compute(version, bytes)` becomes `ids::change_id(version, bytes)`, and `ChangeId::CONTEXT` becomes `ids::CHANGE_ID_CONTEXT`.
- **`receive::Fold`.** `fold` takes the operation's `field_op::Origin` (its id, author and stamp) instead of its `OperationId`, and returns `Result<(), OperationParkReason>`: return `Ok(())`, or the reason the operation parks. Implement `fold_object(object, operation)` to apply a create or delete, for example `self.objects.entry(object).or_default().apply(operation)`, and `clear_field(object, collection, field)` and `clear_object(object)`, which forget a field's state and an object's creates and deletes so that the log can fold the remaining changes into them again after a late revocation. `fold` no longer receives operations without a field.
- **`receive::Checks`.** `verify` returns `Result<(), Stop>` and `open` returns `Result<Payload, Stop>`; the `Verified` and `Opened` enums are gone. Return `Err(Stop::Rejected(reason))` for a failed check, and `Err(Stop::Parked(ParkReason::UnknownPayloadFormat))` for a plaintext that does not decode. `verify` and `open` must keep passing for a change that passed them as control changes arrive; only `is_member` may turn from pass to fail. Most code uses `checks::SealChecks` instead, which verifies and decrypts for real.
- **`SealChecks`.** `SealChecks::new(space, member_key)` has no type parameter and learns the member keys, the membership and the space keys from the control changes the log receives. `add_member`, `add_space_key`, `membership` and the trait `checks::Membership` are removed: deliver the genesis, the membership entries and the key envelopes to the log instead.
- **Membership.** A `match` on `membership::Entry` needs arms for `Entry::KeyEnvelope` (entry type 2) and `Entry::KeyChain` (entry type 3), which no longer read as `Entry::Other`. A `match` on `membership::Rejection` needs `Rejection::DuplicateGeneration`, and one on `membership::Verdict` needs `Verdict::Waiting`, a shred whose causal past the holder does not fully hold yet; treat it as not accepted. `Generation` has a new public field, `holders`: add it to a struct literal, or start from `Generation::default()`. `PreviousKey::key` is `[u8; 72]` instead of `Vec<u8>`.

```rust
let mut checks = SealChecks::new(space, member_key);
log.receive(&frame, &mut checks, &mut fold)?;
let id = ncdb_core::ids::change_id(frame_version, &header_bytes);
```

### The Rust SDK and the CLI on crates.io

<!-- rust-sdk-on-crates-io · tickets: NOC-372 -->

The Rust SDK and the CLI are on crates.io, with the core crates they need, `ncdb-core` and `ncdb-plugin`. Alphas stay off crates.io; to use one, depend on its git tag.

```sh
cargo add nocentraldb@0.1.0-beta.1
cargo install ncdb@0.1.0-beta.1
```

### Models, the lock and `ncdb model build`

<!-- model-build-and-check · tickets: NOC-70 -->
<!-- infer-and-deprecated-collections · tickets: NOC-80 -->
<!-- index-scope-space · tickets: NOC-85 -->
<!-- sdk-ts-lock-out-of-date · tickets: NOC-323 -->

Declare a model with the schema functions of `@nocentraldb/sdk`, build `model.lock.json` from it with `ncdb model build`, and check it in CI with `ncdb model check`. Both run the schema with Node.js 24 or later. A change that clients on an older model could not keep, such as removing or retyping a field, is refused with a message that says why and what to do instead, and nothing is written.

```ts
import { nc } from "@nocentraldb/sdk";

export const model = nc.model({
  teams: nc.collection({ name: nc.string() }).deprecated("Use groups."),
  tasks: nc.collection(
    {
      title: nc.string().describe("One line; what has to be done."),
      status: nc.oneOf(["open", "in_progress", "done"]),
      priority: nc.int(),
      dependsOn: nc.links("tasks"),
    },
    {
      indexes: {
        byStatus: nc.index(["status"], { equal: 1 }),
        byPriorityInSpace: nc.index(["priority"], { scope: "space" }),
      },
    },
  ),
});
export type Task = nc.Infer<typeof model.tasks>; // every field optional
```

```sh
ncdb model build            # reads ./model.ts, writes ./model.lock.json
ncdb model check            # fails if the lock is out of date or the change is not additive
```

`nc.Infer` types an object as the app reads it: every field optional, a choice as its options or `nc.Unknown`, an `nc.int` as a `number`, a set as an array, a link as an object id. `.deprecated(reason)` works on a collection as on a field: the collection leaves the model's type, and the lock records it. An index with `scope: "space"` runs in one space at a time. In the browser, `nc.open` fails with `lockOutOfDate` when the model names a collection, field or index the lock does not have, or with another type or options, so a forgotten `ncdb model build` shows at once.

### References to objects in other spaces

<!-- nc-ref-in-the-schema · tickets: NOC-99 -->
<!-- reference-written-from-both-sdks · tickets: NOC-354 -->

`nc.ref("collection")`, or `nc.ref([...])` with several collections, declares a reference to an object in any space. It takes `.describe(...)` and `.deprecated(...)`, and cannot be personal. Adding a collection to its targets is an additive change; removing one is refused, as for links. Both SDKs write and read it, and a reference written by one reads back on the other.

```ts
// model: customer: nc.ref("customers")
await orders.update(model.orders, orderId, { customer: { space: customers.id, id: customerId } });
(await orders.get(model.orders, orderId))?.customer; // { space, id }; write null to clear it
```

```rust
orders.update("orders", order, [("customer", Value::from(Reference::new(customers.id(), customer)))]).await?;
let customer = orders.get("orders", order).await?.unwrap().get::<Reference>("customer")?;
```

### The TypeScript SDK in the browser

<!-- sdk-ts-in-the-browser · tickets: NOC-176 -->
<!-- sdk-ts-queries-and-subscriptions · tickets: NOC-176 -->
<!-- sdk-ts-change-events · tickets: NOC-176 -->

`@nocentraldb/sdk` opens the member's database in the browser. It starts its own worker, runs the core from the WebAssembly module the package ships, and keeps the database on OPFS under its `name`. Write in a transaction or with the one-call `create`, `update`, `delete` and `restore`; `null` clears a field. Page through every declared index, with the equality prefix checked by TypeScript, and follow a page or one object. A subscription gets the whole page at once and again after every write or sync that touched its collection. The change event tells an app or an agent which objects a fold touched, and whether by its own write, without carrying values. Every error is an `nc.Error` with a `code`, such as `notFound`, `invalidValue` or `closed`.

```ts
import { nc } from "@nocentraldb/sdk";
import { model } from "./model";
import lock from "./model.lock.json";

const db = await nc.open({ model, lock, name: "default" });
const project = await db.spaces.create();
const { ids } = await project.write((tx) => {
  tx.create(model.tasks, { title: "Ship it", tags: nc.add("sdk") });
});

const query = model.tasks.indexes.byStatusPriority.equal("open").take(50);
const page = await db.find(query); // { items, cursor, hasMore }
const stop = db.subscribe(query, (page) => render(page.items));
const stopChanges = db.changes.subscribe(({ space, collection, ids, origin }) => {
  // origin is "local" for this member's writes and "remote" for what sync brought
});
```

A cursor stays on the device, prints as `[redacted]`, and another database refuses it with `cursorOfAnotherModel`. `space.find` reads an index with `scope: "space"`.

### Several browser tabs share one database

<!-- sdk-ts-tabs-share-a-database · tickets: NOC-177 -->
<!-- sdk-ts-waiting-for-tab · tickets: NOC-355 -->

Open the database in every tab as usual. The first tab owns it, the others reach it through the owner, and subscriptions fire in every tab. When the owning tab closes or calls `db.close()`, another tab takes the database over, and every tab reads again what it follows. A write that was in flight while its owner went away fails with `storageFailed` and may or may not have run; read before you write it again. A tab whose `model.lock.json` differs from the owning tab's fails to open with `modelRefused`.

In Safari, a hidden tab that owns the database can be frozen while it holds the storage, and a write from the visible tab then waits until it runs again. `db.durability` reports `waitingForTab: true` once a tab has waited 1 s, so the app can tell the user why nothing is saved yet; `docs/browser-durability.md` has a text for it ("Another tab is open").

```ts
db.durability.subscribe(({ waitingForTab }) => {
  otherTabNotice.hidden = !waitingForTab;
});
```

### What the browser keeps, and what the relay holds

<!-- sdk-ts-durability-and-view · tickets: NOC-315 -->

The SDK asks the browser for persistent storage on open, without waiting; with `persistentStorage: "on-request"` the app asks itself, after its own onboarding text. `db.durability` tells the app how many changes exist only on this device and since when, so it can warn the user before the browser deletes the copy. `db.view` reports whether the view is being rebuilt, and how far.

```ts
const db = await nc.open({ model, lock, persistentStorage: "on-request" });
db.durability.subscribe(({ storage, unconfirmed, oldestUnconfirmedAt, atRisk }) => {
  if (atRisk) warn(`${unconfirmed} changes exist only on this device`);
});
const granted = await db.durability.requestPersistent(); // the browser's answer
db.view.current(); // { rebuild: { folded, total } | null }
```

### Spaces and members

<!-- invitation-text-form · tickets: NOC-180, NOC-141 -->
<!-- member-id-text-form · tickets: NOC-298 -->
<!-- rust-members-list-remove-set-role · tickets: NOC-169 -->
<!-- rust-space-leave · tickets: NOC-216 -->
<!-- sdk-ts-members · tickets: NOC-176 -->
<!-- sdk-ts-spaces-subscribe-and-leave · tickets: NOC-315 -->
<!-- sdk-rust-spaces-subscribe · tickets: NOC-256 -->
<!-- sdk-rust-member-linked-to · tickets: NOC-269, NOC-307 -->
<!-- sdk-ts-member-linked-to · tickets: NOC-269, NOC-307 -->
<!-- sdk-rust-merge-rotation · tickets: NOC-220 -->

A member shares its invitation as text (`ncdb-invite-1:…`), by a QR code, a link or a message. An admin adds its member to a space; for an account new to the admin's device, a person compares the fingerprint on both screens once. Both SDKs list a space's members, change a member's role, remove a member and leave a space, and follow the list of spaces as it changes, so an app learns at once that another device shared a space with this member. A member id prints and parses as 64 lowercase hex digits, so an app can store it.

```rust
let text = db.invitation().await.to_string();
// on an admin's device:
let invitation: Invitation = text.parse()?;
space.members().add(&invitation, AddMember { role: Role::Writer, fingerprint: Some(invitation.fingerprint()) }).await?;

let dan = space.members().list().await?.into_iter().find(|m| !m.is_self).unwrap();
space.members().set_role(dan.id, Role::Reader).await?;   // NoticeCode::RoleSet
space.members().remove(dan.id).await?;                   // NoticeCode::MemberRemoved
let mut spaces = db.spaces().subscribe();                // the list at once, then each change
```

```ts
const project = await db.spaces.get(id);
try {
  await project.members.add(nc.invitation(text), { role: "writer" });
} catch (error) {
  if (error.code !== "unknownAccount") throw error;
  if (await askPersonToCompare(error.fingerprint)) {
    await project.members.add(nc.invitation(text), { role: "writer", fingerprint: error.fingerprint });
  }
}
const stop = db.spaces.subscribe((all) => showSpaces(all)); // [{ id, role, model: "ours" | "another" }]
const { notice } = await project.leave(); // notice.code === "spaceLeft"
```

Removing a member rotates the space key, so the removed member cannot read what is written afterwards; it keeps its copy of everything it received before. Giving a reader the right to write again rotates the key first. Only an admin removes members or raises a role; any member may lower its own role or leave, except the space's last admin (`lastAdmin`). A member that leaves does not rotate the key, since it must not know the next one: an admin's SDK that syncs sees the exposed key and rotates it on its own after a random delay of up to a minute, and `status().exposed` turns false once the rotation is folded.

Each member also carries `linked_to` in Rust and `linkedTo` in TypeScript: the account its old account is linked into, when this database knows the link from its own account. Another person's links are not known yet, so their members show none.

### Writing and reading in Rust

<!-- sdk-rust-restore-and-space-shorthands · tickets: NOC-277 -->
<!-- sdk-rust-clear-and-page-limit · tickets: NOC-277, NOC-274 -->

A space has one-call shorthands for a single write, each one change, and a deleted object can be restored. `Value::clear()` clears a basic field or a link, as `null` does in TypeScript; a clear of a set or of many links fails with `InvalidValue`. A page of a query takes up to 1000 objects in both SDKs.

```rust
let written = project.create("tasks", [("title", Value::from("Ship it"))]).await?;
let task = written.ids[0];
project.update("tasks", task, [("title", Value::clear())]).await?;
project.delete("tasks", task).await?;
project.restore("tasks", task).await?;
let page = db.find(db.index("tasks", "byPriority")?.take(1000)).await?;
```

### Sync through a relay

<!-- rust-sync-follow-pause-confirm · tickets: NOC-120 -->
<!-- sdk-ts-sync-and-status · tickets: NOC-176 -->
<!-- sdk-rust-wss · tickets: NOC-121 -->
<!-- sdk-rust-large-changes · tickets: NOC-121 -->
<!-- relay-large-changes · tickets: NOC-102 -->
<!-- rust-sync-push-refused-change-again · tickets: NOC-120 -->
<!-- a-removed-member-folds-its-own-removal · tickets: NOC-383 -->

Both SDKs follow the relay connection as a stream, pause and resume syncing to keep a database offline on purpose, and tell when the relay holds a write. Waiting for that may never end, since the relay can refuse the change or never be reached. The Rust SDK connects to a relay over `wss://`, verifying its certificate against the platform's trust store.

```rust
let db = Db::open(OpenOptions::new(LOCK).path("data").relay("wss://relay.example.com")).await?;
let mut statuses = db.sync().subscribe();
db.sync().confirmed(written.change).await;
db.sync().pause().await;
db.sync().resume().await;
```

```ts
const db = await nc.open({ model, lock, relay: "wss://relay.example.com" });
const stop = db.sync.subscribe((status) => showConnection(status.connection));
await db.sync.confirmed(change);
```

A change too large for one 128 KiB message, such as a large paste, goes through the relay as an upload of up to 16 MiB, and the relay checks it like any other change; the local relay takes `--public-url https://relay.example.com` when it runs behind a TLS proxy. A change the relay refused because of a revocation is pushed again once a concurrent change makes the revocation ineffective. A member removed while it was offline now receives its own removal: its writes after the cutoff become rejected on its own copy too, and `space.status()` counts them under `rejected` with `NotMember`.

### The local relay admits an app's accounts by invitation

<!-- relay-allow-invitation · tickets: NOC-257, NOC-239 -->
<!-- relay-guest-account-one-space · tickets: NOC-283 -->

Start the local relay with the text of one of the app's invitations, and it lets that invitation's account create spaces. The flag may be given more than once and combines with `--allow-account`; a text that is not an invitation stops the relay at start with exit code 2. A guest invited into a space of a listed account may create exactly one space of its own, its account space, which its devices need once it pairs a second one.

```text
ncdb-relay --database relay.sqlite --allow-invitation "ncdb-invite-1:Aa8Go-Mp…"
```

### What a space holds that a read does not show

<!-- rust-space-status · tickets: NOC-190 -->
<!-- rust-space-status-equivocations · tickets: NOC-190 -->
<!-- rust-space-status-newest-model · tickets: NOC-197 -->
<!-- writer-model-key-64 · tickets: NOC-197 -->
<!-- plugin-unknown-type · tickets: NOC-248 -->
<!-- sdk-rust-bad-person-key-records · tickets: NOC-206, NOC-222 -->

`space.status()` reports, at once and after every change, the member's role, whether the first sync is complete, how far behind it is, gaps, parked and rejected changes counted per reason, the member's own changes the relay refused, lost grants, whether the space key is exposed, and whether the space waits for a key. TypeScript reads the same from `project.status`.

Every change names the model that wrote it, inside the encrypted payload. A member parks a change of another app's model whole, under `ParkReason::AnotherModel`, and `newest_model` gives the highest version of the app's own model that its parked data needs, so an app can ask its user to update. An operation on a plugin field whose type no code implements parks under `ParkReason::UnknownType`. `equivocations` lists two different changes of one author under one sequence, as a device restored from a backup or cloned writes. `bad_person_key_records` names the accounts whose person-key records failed their checks.

```rust
let status = project.status().current();
if status.newest_model.is_some_and(|needed| needed > MY_MODEL_VERSION) {
    show("Some data needs a newer version of this app");
}
if !status.equivocations.is_empty() {
    show("A device of this space writes from two places");
}
```

### Opening after a model change does not block the app

<!-- additive-model-change-migrates-the-view · tickets: NOC-156 -->
<!-- view-rebuild-in-the-background · tickets: NOC-156 -->

When the lock only adds to the model, such as a new field, collection or index, the view is migrated in place, and only the changes parked for the additions are folded again. When the whole log must be folded again, as after an app was rolled back to an older model, `Db::open` returns at once: the app reads the old view meanwhile, and `db.view()` reports the rebuild's progress until the new view is swapped in.

```rust
let mut view = db.view().subscribe();
while let Some(status) = view.next().await {
    match status.rebuild {
        Some(progress) => show_progress(progress.folded, progress.total),
        None => break,
    }
}
```

### Accounts: recovery code, pairing and lost devices

<!-- sdk-rust-recovery-code-and-pairing · tickets: NOC-267, NOC-285 -->
<!-- sdk-rust-pair-device-and-recover · tickets: NOC-267 -->
<!-- sdk-rust-link-account-when-pairing · tickets: NOC-267, NOC-291 -->
<!-- remove-a-lost-device · tickets: NOC-268, NOC-236 -->
<!-- account-key-statement-entry · tickets: NOC-233 -->
<!-- sdk-ts-recovery-code · tickets: NOC-316 -->
<!-- sdk-ts-pairing · tickets: NOC-316 -->
<!-- sdk-ts-remove-member · tickets: NOC-316 -->

A person's laptop, phone and agents belong to one account. The first open of a database creates its account and a recovery code of twelve words; the app shows it until the person confirms they stored it. A new device or an agent opens its database for pairing, carries its invitation to a device of the account and the answer back. A paired device joins every space where the pairing device is an admin, and the account space; for the other spaces the app asks their admins. An agent receives a certificate only, never the account key. A database that already had an account of its own is linked into the person's account when it is paired. An account whose every device was lost comes back on a new device from its recovery code: the device holds a new account key, keeps the account's fingerprint, and is a member of no space until other members add it.

```rust
if let Some(code) = db.account().recovery_code().await? {
    show(code.words());
    code.confirm().await?;
}
let phone = Db::open(OpenOptions::new(LOCK).path("./data").pairing()).await?;
let paired = laptop.account().pair(PairKind::Device, &phone.invitation().await).await?;
let notices = phone.account().complete_pairing(&paired.answer).await?;
let recovered = Db::open(OpenOptions::new(LOCK).path("./data").recover(&words)).await?;
```

```ts
const code = await db.account.recoveryCode(); // null once confirmed
const fresh = await nc.open({ model, lock, pairing: "request" });
const { answer, added, askAdmins } = await db.account.pair({ kind: "device", invitation: nc.invitation(text) });
const { notices } = await fresh.account.completePairing(nc.pairingAnswer(answerText));
const recovered = await nc.open({ model, lock, recover: words });
```

When a device is lost, another device of the account removes it with the recovery code: from every space it administers and from the account space, and it renews the account key. Every space then learns the new key, and refuses an add certified by the old account key, or an erasure signed off by it. A recovery code that is not the account's removes nothing and is refused with `NotAllowed`.

```rust
let removed = db.account().remove_member(lost, &words).await?;
// removed.removed: the spaces it was removed from; removed.ask_admins: the spaces whose admins to ask
```

```ts
const { removed, askAdmins, notice } = await db.account.removeMember(lostDeviceId, { recover: words });
```

An agent that has an account of its own cannot be linked into a person's account yet: pairing it fails with `NotAllowed`.

### Personal fields and erasing a person

<!-- core-personal-value · tickets: NOC-244 -->
<!-- core-view-personal-fields · tickets: NOC-244 -->
<!-- sdk-rust-personal-write · tickets: NOC-244 -->
<!-- sdk-rust-personal-read · tickets: NOC-244 -->
<!-- sdk-rust-erase-a-person · tickets: NOC-325, NOC-326 -->
<!-- shred-final-when-accepted · tickets: NOC-229, NOC-224, NOC-228 -->
<!-- sdk-drops-shredded-person-key · tickets: NOC-229, NOC-224 -->

A personal field is sealed under the key of the person it is about, so destroying that key erases the value on every member. In Rust, write it like any other field; the schema's `person` names the person, the object itself or the target of its person link. `Create { same_person_as: Some(object) }` records the same person as an object in another space, so that one erasure reaches both. A read opens the value with the person key this device holds; until syncing fetches it, the field reads as unset, and a write is refused with `PersonKeyNotHeld`. After an erasure the field reads as unset on every device, `object.erased()` names it, and the view drops the person's values from its indexes at once.

To erase, name the person by one of their objects, have a device of a second account sign the request off, and erase in every space of the database:

```rust
let request = db.erasure_request(&anna).await?;                 // text: ncdb-erase-1:…
let signed = other_device.account().sign_off(&request).await?;  // text: ncdb-sign-off-1:…
let erased = db.erase(&request, &signed.sign_offs).await?;
```

An erasure is final as soon as a member or the relay accepts it: no later revocation undoes it, the relay deletes the key's record, and an open member drops the key from memory at once. When the performer's account is the only one with an admin, a writer of another account can sign off; a reader's account never can.

### Erasures in a space of one account

<!-- provisional-erasure-core · tickets: NOC-234 -->
<!-- sdk-rust-provisional-erasures · tickets: NOC-234 -->
<!-- relay-too-early · tickets: NOC-234 -->
<!-- erase-again-after-take-back · tickets: NOC-258 -->

In a space whose members all belong to one account, a device of that account signs the erasure off itself, and the erasure is provisional for 7 days: the person shows as erased, but members keep the key. `status().provisional_erasures` lists it on every device of the account, and an app must show it, since that is how the owner notices an erasure by a stolen device. `space.erasures().take_back(shred)` takes it back within the 7 days. After 7 days an admin device of the account finalizes it on its own, and members then destroy the key; the relay refuses a finalize sooner with `too_early`. A person whose erasure was taken back can be erased again, with its own 7 days.

### Auditing an erasure

<!-- erasure-acknowledgements · tickets: NOC-238 -->
<!-- erasure-audit · tickets: NOC-246 -->
<!-- sdk-ts-space-erasures · tickets: NOC-315 -->
<!-- erasures-list-a-waiting-shred · tickets: NOC-401 -->

Every member that folds an erasure writes that it saw it and then that it deleted its copy of the key, and syncs it. `erasures().list()` in Rust and `erasures.list()` in TypeScript give, for each erasure of a space, its state (final, provisional, taken back or waiting), who performed and who signed it off, and each member with `deleted`, `seen` or `missing`, so an app can show which device never answered. Every member may read it, a reader too.

An erasure that arrives before changes it depends on has no effect until sync brings them. It is listed as `waiting`, with its performer and its sign-off and no members, and then moves on to final, provisional or taken back, or leaves the list if it is rejected. `ncdb-core`'s `Resolved::waiting_shreds()` gives the same.

```ts
const erasures = await project.erasures.list();
// [{ shred, state, performer: { id, account }, signOff,
//    members: [{ id, account, current, acknowledged: "deleted" | "seen" | "missing" }] }]
for (const erasure of erasures) {
  if (erasure.state === "waiting") showSyncing(erasure.shred);
}
```

### Ad-hoc spaces and sub-agents

<!-- ad-hoc-spaces · tickets: NOC-318 -->
<!-- ad-hoc-spaces-in-typescript · tickets: NOC-318 -->
<!-- sub-agent-identity · tickets: NOC-318 -->

An agent that hands part of a task to a sub-agent creates an ad-hoc space: a new space with a fresh key, holding a copy of only the objects the task needs, each under a fresh id. A link to an object copied too points to its copy; any other link is cleared, so no id of the original space reaches the sub-agent. Personal and plugin fields are not copied. The agent finds the pairs again on its own database, to write the results back. A sub-agent in Rust opens its database with `OpenOptions::sub_agent()`, and its parent adds it with `Members::add`, signing its certificate, so it answers through its parent to the account and never holds an account itself.

```rust
let created = db.spaces().create_ad_hoc(AdHoc { copy, ..AdHoc::default() }).await?;
```

```ts
const task = await project.get(model.tasks, id);
const { space, notice, copies } = await db.spaces.createAdHoc({ copy: [task] });
```

Opening a database as a sub-agent in TypeScript comes with the SDK in Node.js.

### Plugin field types

<!-- ncdb-plugin · tickets: NOC-248 -->
<!-- sdk-plugin-fields · tickets: NOC-250, NOC-84 -->
<!-- ncdb-harness · tickets: NOC-249 -->
<!-- plugin-config-refused · tickets: NOC-251 -->

A field can have a type a plugin implements. A plugin is a crate that depends on `ncdb-plugin`, implements `FieldType` for each of its types, and exports `plugin()`. The Rust SDK takes it with `OpenOptions::plugin`; a plugin field reads as `Data` and is written with a `Data` intent. A write to a field whose type no plugin given implements is refused with `UnknownType`, and once the database is opened with the plugin, it folds what was parked. A plugin's crate checks its type for convergence with `ncdb-harness`, from this repository, natively and on wasm32. `ncdb model build` refuses a change of a plugin field's `config`, since members would merge existing values differently: add a new field and deprecate the old one.

```rust
let db = Db::open(OpenOptions::new(LOCK).path("./data").plugin(acme_ncdb_counter::plugin())).await?;
space.write(|tx| tx.update("tasks", task, [("votes", Value::from(Data::Integer(1)))])).await?;
```

### Building blocks in `ncdb-core`

<!-- membership-resolve · tickets: NOC-67 -->
<!-- re-grants-and-the-generation-graph · tickets: NOC-71 -->
<!-- current-generation-exposure-and-merge-rotations · tickets: NOC-86 -->
<!-- fold-creates-and-deletes-objects · tickets: NOC-39 -->
<!-- member-log-real-checks · tickets: NOC-48 -->
<!-- checks-learn-from-control-changes · tickets: NOC-78 -->

For code below the SDKs, `ncdb-core` provides what they are built on: `membership::resolve`, which folds a space's control changes into its membership, roles, generation graph and current generation, the same in any order of arrival; `checks::SealChecks`, which verifies and decrypts received changes; the member log, which folds creates and deletes of objects and folds again when a late revocation removes a member's changes; and `view::View`, a member's database on SQLite with its log and the view folded from it.

```rust
let state = membership::resolve(space, &control_changes);
let mut view = View::open(path, &lock)?;
view.receive(&frame, &mut checks)?;
let page = view.page("task", "byRank", &[], None, View::DEFAULT_PAGE)?;
```

## Security

### The relay stops serving a member a later removal excluded

<!-- relay-drops-a-member-resolve-no-longer-names · tickets: NOC-390 -->

The relay kept serving a member whose add a later removal excluded, for example an accomplice that a stolen admin device added before the owner removed that device with a cutoff below the add. It accepted the member's uploads, served it pulls, listed the space for it, and admitted changes it had written before. Now, when a control change drops a member out of the space's membership, the relay refuses all of these. Both the local and the AWS relay get the fix. On a relay that ran an alpha, a member that should have been dropped before the fix stays until the next control change in its space.

**Advisory.** pending

### Two account keys of one person cannot sign off each other's erasures

<!-- sign-off-account-by-recovery-key · tickets: NOC-196, NOC-201, NOC-132 -->

An erasure needs a sign-off by an admin of another account than the performer's. The fold now treats two account keys as one account when any certificate in the erasure's causal past attaches the same recovery key to both, so the old and the new account key of one person after a recovery cannot sign off each other's erasures. A statement in a certificate can only block a sign-off, never enable one.

**Advisory.** pending

## Known issues

### The TypeScript SDK cannot erase a person or use plugin field types yet

In the browser, the TypeScript SDK cannot request, sign off, erase or take back an erasure of a person; it can list and audit erasures. It also has no plugin field types. Both work in the Rust SDK and are planned for a later beta (NOC-406).

### A new tab in Safari waits in `nc.open` while the tab that owns the database is frozen

If the user opens a new tab while the tab that owns the database is hidden and frozen, `nc.open` in the new tab waits until the other tab runs again. There is no `db` yet, so `db.durability.waitingForTab` cannot report it, and the app sees only a slow open (NOC-356). The open goes on once the other tab runs again, for example when the user switches to it.

### `space.inspect` is missing, and `$erased` in TypeScript

RFC 0005's `space.inspect`, which tells whether a reference's target is there, in a space this member holds no copy of, or gone, exists in neither SDK, and a TypeScript read object has no `$erased` (NOC-375). Workaround: `notFound` from `db.spaces.get` means the target's space is not held, `$deleted` marks a deleted target, and `undefined` a target that has not arrived yet. An erased personal field reads as unset in TypeScript; Rust has `object.erased()`.

### `ncdb-plugin` prints a redacted value as `<redacted>`

The other crates print `[redacted]` (NOC-377). Both mean the same.
